Where does the chat's memory come from?

You asked that the cycle chat should have "the context of the Claude session related to it". This page shows why it cannot be written into your open terminal session, and the three ways to give the chat that context, each tried on the same example.

First: what happens today

You start Claude Code in a terminal and type /alfred-live "Branch search". That terminal session is your Claude Code session - it has the whole morning in it: what it read, the files it changed, what you decided.

/alfred-live then starts a small runner in the background (alfred-live.mjs). When you comment on a card, the runner does not type into your terminal session. It starts a separate, fresh claude run that sees only that comment and the card's recent thread, answers, and ends.

Why not just send chat messages into the terminal session?

A Claude Code session is one conversation held by one process - your terminal. Alfred cannot type into it, and a second process cannot safely add turns to it while it is open:

  • Two writers, one session file: the terminal and a chat answer would both append to the same conversation - turns interleave, and one can overwrite the other's state.
  • Your terminal would not see it: the open terminal keeps its conversation in memory. Turns added from outside do not appear there until you restart it - so it would "forget" the chat anyway.
  • It would block you: while you are working in the terminal, a chat message would have to wait for your turn to end, or interrupt it.

So the chat needs its own conversation that starts from your session's memory. The question is how.

The example used for all three

Morning, in your terminal: Claude investigated #49, you agreed "dates are compared in UTC", and it changed BranchFilter.java to read branchId (singular). It never wrote the UTC decision to the board.

12:20, in the board chat: you ask two things:

  1. "Why did you change BranchFilter?"
  2. (later) "And what did we decide about the dates?"

13:00, in your terminal: you ask Claude to also fix the export. Then in the chat: "Did the export fix land?"

The three ways

How it works

  1. Your first chat message: the runner makes a copy ("fork") of your terminal session - its whole memory up to now - as a new chat session. Your terminal session is not touched.
  2. That copy answers. Every later chat message continues the same copy, so the chat is one real conversation that remembers the morning and every chat turn.
  3. When your terminal did more work since, the chat header offers "Refresh from session": a new copy is taken; the chat's own history is carried over by the compact summary.
# first message claude -p --resume <terminal session> --fork-session → chat session X # every later message claude -p --resume X
You · 12:20
Why did you change BranchFilter?
Claude · 12:20 remembers
This morning we found the UI sends branchId but the filter read branchIds, so it filtered nothing. I changed line 42 to read the singular field - that's the fix for #49.
You · 12:31
And what did we decide about the dates?
Claude · 12:31 remembers
Compare in UTC - you agreed at 10:15. Want me to write it to the brief so it sticks?
You · 13:10
Did the export fix land?
Claude · 13:10 needs refresh
I don't see an export change since this chat started (12:20). Your terminal session may have done it after - press Refresh from session and I'll check.

Cost: the first message reads the whole session (the cache makes later ones cheap). The chat conversation grows; Alfred's compact keeps it in check, and a refresh starts a new copy.

How it works

  1. Every chat message gets a fresh run - like card comments today.
  2. The runner hands it Alfred's context (the chat's summary and recent messages, the brief, the cards) plus a short digest it reads from your terminal session's transcript file on disk (the last steps and decisions).
  3. No conversation grows; nothing is resumed.
# every message claude -p "<Alfred context> + <digest of the session transcript> + <your message>"
You · 12:20
Why did you change BranchFilter?
Claude · 12:20 from a digest
The session's notes say BranchFilter.java was edited to read branchId for #49. I don't have the reasoning behind it beyond that.
You · 12:31
And what did we decide about the dates?
Claude · 12:31 may miss it
I don't see a date decision in the board or the digest. If it was in the terminal conversation, it may not have made the digest.
You · 13:10
Did the export fix land?
Claude · 13:10 always fresh
Yes - the session's latest steps show RefundExport.java edited at 13:02.

Cheapest and always sees the latest terminal work, but the memory is a summary: details and reasoning that were only said in the conversation can be lost.

How it works

  1. Every chat message makes a new copy of your terminal session and answers from it.
  2. So each answer knows everything the terminal did up to that moment.
  3. But each copy is new: earlier chat turns are only known through Alfred's chat history passed in the prompt.
# every message claude -p --resume <terminal session> --fork-session "<chat history> + <your message>"
You · 12:20
Why did you change BranchFilter?
Claude · 12:20 remembers
The UI sends branchId, the filter read branchIds - line 42 now reads the singular field (#49).
You · 12:31
And what did we decide about the dates?
Claude · 12:31 remembers
UTC - agreed at 10:15.
You · 13:10
Did the export fix land?
Claude · 13:10 always fresh
Yes - RefundExport.java was changed at 13:02 in the session.

Best answers, highest cost: every message re-reads the whole terminal session (a long morning can be hundreds of thousands of tokens each time; the cache helps only within minutes). Many copies pile up in Claude Code's session list.

Recommendation

A · Fork once, continue the fork. It is the only way that gives the chat the terminal session's real memory and a real conversation of its own, at a low cost per message, without ever touching your terminal session. Its one gap - work your terminal does after the chat began - is covered by Refresh from session, and the chat header shows when the terminal session has newer work than the chat's copy ("session moved on · Refresh").

If a cycle has no terminal session (you never ran Claude Code for it, or it was on another machine), A starts the chat's own session from Alfred's context and continues that - the same as the project chat.
