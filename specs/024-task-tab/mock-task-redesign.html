Requirements - what the task must do, and whether the code does it hide ✕

Each row is one Acceptance line of the spec file (the ticket's criteria). Alfred judges a row from the calls you record while using the app; when the calls can't show it, you decide with Pass / Fail / Can't tell. Your mark is what counts - Claude only suggests.

What the states mean
  • ✓ MET the calls (or your Pass) show it works
  • BUG it was built but the calls show it wrong - a card holds the fix
  • MISSING nothing in the calls does it yet - a task, not a bug
  • RE-TEST a fix is in - use the app as the card says, then verify
  • CAN'T TELL calls exist but can't prove it (e.g. 0 rows came back)
  • NOT CHECKED no call has tried it yet
  • ✦ SUGGESTS Claude has an answer from the code - you accept or not
How to decide a row
✦ Claude suggests →read its reason (open the row). Agree? Accept. Not sure? check it in the app first. 0 rows →the search ran but found nothing, so nothing could be checked. Can't tell with a note why - it stays open in Done when.

How to test it

The brief's Test steps. Do them in the app while Claude listens (Run ▾ → Check while I test): a step gets ✓ and its calls when Claude sees them, ✗ with a card when it went wrong, not yet until then. Test data says what the steps need - set it up first, or searches come back with 0 rows.

Done when

The rule for handing the task over. All three must be ✓: every requirement marked by you, no open bug or task card, every fix re-tested. Then Hand-over report writes the summary for QA. A ✗ tells you what is left - click it to go there.
