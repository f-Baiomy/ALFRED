Step checks as rule conditions - with fail / warn

"Check the response" is the rule editor's own IF block: the same condition row component, subjects, list modes and operators, evaluated by the same proxy Condition code as a rule. Each check says what a miss means - fail and stop the run or warn and carry on - with one default for the whole block. The "On the recording" preview stays. Resend scenarios are not touched. Click the tabs, and the "on fail" dropdowns.

AND / OR

  • Checks come in groups. Each group is the rule IF block itself, with its existing all of / any of switch: rows joined by AND or OR (click "all of" in the mock to flip it).
  • Every group must pass. A group with one row is a single check.
  • "On a miss" (fail / warn) belongs to the group - inside an OR group there is no single row to blame, the group as a whole passes or not.
  • The proxy already evaluates a branch as "all of / any of" its conditions, so a check group is evaluated by exactly that code - no new combining logic.

Fail or warn

  • Default ("When a check misses (default): …") applies to every group set to as block default. Each group can override it.
  • Fail · stop the run: the step is marked failed and the run holds there (the same hold box as today: Retry / Continue with the next calls / End run). An optional step only gets marked failed - it never stops the run, as today.
  • Warn · continue: the step is marked passed with warnings, the run goes on, and the run summary and run log count the warnings.
  • A step with no checks behaves as today (passes when the answer matches the recording after noise).

One editor, one evaluator - and the preview kept

  • Editor: the condition row moves out of app-rule-editor into app-condition-row, used by the rule editor's IF and by step checks. A subject, operator or list mode added there shows up in both. The fail / warn dropdown is a check-only extra at the end of the row.
  • Evaluator in a run: the proxy's Condition class runs a step's checks when its call answers and reports each result (and what it found), next to the rules it already reports.
  • "On the recording" preview: evaluated by the same proxy code, not a browser copy. The page asks the backend, which sends the checks and the recorded response through the proxy to a reserved internal address the addon answers itself (never forwarded anywhere). Refreshed as you edit, after a short pause. If the proxy is down the line says "preview unavailable".
  • Response time (ms) new becomes a condition subject - rules get it too. Checks offer only response subjects; request subjects stay rule-only.

Header and cookie suggestions (tab 4)

  • One name-suggestion dropdown (app-name-suggest) under every header or cookie name box: step checks, the rule editor's IF conditions and header / cookie actions (inline in box 5 and in the rule dialog - the same component), and Values' "Save a value" from Header / Cookie.
  • Where the names come from: the step's recording - request headers and the request Cookie header for request-side boxes, response headers and Set-Cookie for response-side boxes. On the Interception page (no step) the rule editor's sample call is used the same way.
  • Each suggestion shows the recorded value as a preview (secrets masked), filters as you type (case-insensitive, match highlighted), ↑↓ / Enter / Esc, and any other name can still be typed.
  • Cookie parsing reuses the existing parseCookieHeader / parseSetCookieHeader (shared/utils/capture-preview.ts).

Not changed

  • Resend scenarios keep their own checks and editor (app-scenario-assertion-editor) exactly as they are.
