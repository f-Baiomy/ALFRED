5.6 s with nothing happening after the supplier calls returned · 27% of the call
Between the last supplier response (#62, at 11.7 s) and the next query (#63, at 17.3 s) the application ran no SQL and called no supplier - so it was computing: most likely parsing and merging the 12 supplier responses (1.7 MB of JSON).
→ Profile that step: GenericDAOImpl.executeBulkSqlQuery:2059 is the code that ran next.
✕
A stored procedure is missing - the error was swallowed · the call still answered 200
#84 LOG_FLIGHTSEARCH_HIT_DETAILS_SP_V6 failed: PROCEDURE wonderdb.FLIGHTSEARCH_HIT_FILTER_AND_LOG_INTERVAL_RATIO does not exist (SQLState 42000). The application caught it, so nothing was logged for this search - and nobody was told.
→ Create the procedure in this database, or stop calling it.
🔁
Same procedure called 12 times, once per supplier · 0.72 s · could be 1 call
LOG_SUPPLIER_ACTION_SP_V1 runs once per supplier response, back to back (#63-#74). Each call pays the ≈ 54 ms trip to the database; the procedure itself takes ≈ 5 ms.
→ Batch the 12 rows into one call (or one executeBatch) - saves ≈ 0.65 s.
🔑
2 Sabre calls were rejected - 401 Unauthorized · results missing from this search
api.platform.sabre.com (production) answered 401 to the token and to the shop request; the cert endpoint answered 200. Production Sabre credentials are wrong or expired. Also: ndc-supplier-integration-staging disconnected.
→ Check the Sabre production credentials for this agency.
ℹ
The database is far away: ≈ 54 ms per round trip · 74 statements ≈ 4.0 s of it
Even a primary-key lookup takes ≈ 54 ms here, so every extra query costs ≈ 54 ms. This makes the repeated calls above expensive; production may be faster.
Also: 36 transactions · 1 rolled back · 3 queries over 100 ms (#48 508 ms, #35 140 ms, #84 116 ms) - all 7 notes
