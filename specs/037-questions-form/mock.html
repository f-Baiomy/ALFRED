Endpoints

POST /board/boards/{id}/questions-form{cards?, lang?, title?} → the HTML file (attachment). Records formId + keys + question hash (board.db table question_forms).
POST /board/files.html accepted only when it parses as an answers file; stored; served Content-Disposition: attachment, application/octet-stream, nosniff, CSP sandbox. Never inlined.
GET /board/files/{id}/answers.jsonparsed JSON.
POST /board/boards/{id}/answers-import{fileId | text, dryRun=true} → JSON + per-answer report. dryRun:false records as user, with source line.

Open points I'd decide in the spec

  • Answers point by id only: q = question id, choice = option ids. Alfred resolves them through the questions it stored under formId (question id → card/entry/header, option id → label). A label edit in the file cannot change the meaning.
  • GET /board/files/{id}/answers.json returns the joined view: each answer with its card, question text and chosen labels beside the ids.
  • "Changed" = the board question now differs from the stored one (text or options) → withdrawn-or-changed.
  • "Already answered": any answer on the board for that key, even a different one. File never overwrites.
  • UI strings: Arabic kept from the reference (Egyptian), English new. Page dir = UI language; every board-written text dir="auto", names in <bdi>. Board buttons follow the same rule (the repo's autoDir directive).
  • "Other answer" = other: true; its text is the note (no second box). Download warns when it is empty.
  • "Not sure, ask me later" = later: true: nothing is applied, the question stays open, and the board shows "Ahmed: later" on it.
  • sure (sure / likely / not sure) goes on the card with the answer, so Claude knows how hard to lean on it. A follow-up answer is applied with its parent.
  • Answers file tags each answer "As recommended" or "Not the recommended" and counts them at the top, so the user sees at a glance where the BA disagreed.
  • Upload of html also allowed on a card (same check); preview always from JSON.

Skill rules (skills/_shared/rules.md, "Asking well")

Asking well - a question must stand on its own for someone who was not there:
- question: one line, the decision only. why: one line, what it blocks.
- details: the evidence, in this order, only what helps decide:
  1. what the user sees - a screenshot, boxes/arrows on the part that matters (board_image_put)
  2. what happened - the call(s) as @[call:…] or ```calls, the rows as a small table
  3. how much / how often - ```stats or ```chart from real numbers, never made up
  4. what the spec says - the Acceptance lines quoted, with their ids
- each option: then (what you will do), preview (what changes, the calls and items it touches).
- mark the one you advise recommended, and say why in its preview.
- no secrets or variable values in text or on a picture - crop or blur before board_image_put.
- for someone outside Alfred: board_questions_form; an uploaded answers file: board_import_answers.
