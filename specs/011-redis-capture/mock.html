Redis linked to calls

mockspecs/011-redis-capture

Every Redis command the application sends while it serves a call - recorded by the same agent that records its database statements and catches its log lines, and shown with them: on the call card, in the call's window, on the timeline, in Findings, in exports and to Claude. Updated: Spring Cache origin, decoded values, who wrote a cached value, value before a write, value tracing, MULTI/EXEC groups, pool wait, health views and one model for every store. Everything here is Alfred's own stylesheet; the parts that are new are drawn with a dashed outline.

Try it: switch views, filter Misses, search fare:rule, open a command. Together tells the story in one list - "cache:supplier-airports missed, so the 738-row SELECT ran, then the result was SET back". Nine single GET fare:rule:* commands in a row fold into one GET ×9 group, like the CRITERIA ×2 group of statements; INCR + EXPIRE sent as one MULTI … EXEC fold into one transaction row, like a TX. Every command and reply is stored in full, byte for byte, whatever its size - Alfred never truncates call data, and a later replay needs the exact reply.

Open a command to see what is new in its detail: Spring Cache - which cache and which method sent it (the CACHE / PUT tag on the row); value format - Java values decoded (JDK serialization, Kryo, Jackson, gzip/Snappy) with Decoded / Raw bytes; written by - on a hit, the earlier call that wrote that key (open GET fare:rule:EK inside the GET ×9 group); before the write - what a SET / INCR / EVAL replaced; trace a value - click a5b4f2f0 on SET upsell:a5b4f2f0 to see everywhere else it appears in the call. The Keys view adds who last wrote each key.

What is recorded per command: the command and every argument, its reply (or the error), the key(s), sizes in and out, the time it was sent and how long the reply took, the client and connection, the database index, the thread, and the code line that sent it - all in full, binary values byte for byte. Not recorded: commands sent outside a call (schedulers, warm-up), and subscribers' incoming messages - only the PUBLISH the call sent.
6 · How it works - where it fits in what Alfred already has
Capture - the db-agent, not a proxy. Redis speaks its own protocol, not HTTP, so the proxies cannot see it. The agent already knows which call each request thread serves (X-Alfred-Call); it gains hooks on the Redis clients in the JVM - Lettuce (command dispatch), Jedis (Connection.sendCommand/reply read) and Redisson (command executor). Lettuce replies arrive on a Netty thread, so the call is taken when the command is sent (on the request thread) and carried with it. Like JDBC capture, the agent never changes what the app sends and runs no command of its own.

Order. Commands share the call's seq counter with statements and supplier calls, so Together needs no guessing.
Storage. Sent with the statements in the agent's batches to backend-db-capture and kept in db-capture.db (a store_commands table beside the statements - see section 8), so session cycles and imports keep them the same way.

Exports. .md / .html get a "Redis" section per call; .json (alfred-calls/3) gets redis records next to dbRows and re-imports them. Nothing truncated.

Claude (MCP). redis_commands and redis_overview for one call; investigate_call and problem_calls include Redis failures and misses.

8 · Built for more than Redis - one model for every store the app talks to
Commands are stored as store commands, not Redis-only rows, so the next store reuses the chip, the lane, the view, Findings, exports and Claude's tools:

store_commands(call_id, seq, store 'redis'|'kafka'|'mongo'…, command, key, args_raw, reply_raw, reply_type,
               fingerprint, error, sent_at, micros, client, connection, db, thread, code_origin, origin 'spring-cache:fareRules',
               before_raw, run_tag)
Raw bytes + reply type + fingerprint + seq + run tag are kept exactly, so a later Relive can answer from them.
