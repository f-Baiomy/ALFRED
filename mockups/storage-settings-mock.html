Where the space goes NEW

Relive cycles NEW

Each run records its calls in its own run recording. They live apart from your session cycles: cleaning one never touches the other. A run you starred or commented on is always kept.

Runs are also cleaned automatically - see Automatic cleanup.

Mock notes - what changes vs today

  • Lists every store. Today's table misses db-capture.db (DB statements, Redis, caught logs), triage.db, relive.db, scenarios.db and interception.db.
  • Shows empty space per file (SQLite free pages) and a Compact action (VACUUM). That is why logs.db shows 1.5 GB with 0 lines.
  • Targeted cleanup (age / project / status / host) with a live preview of count and freed size. Calls with comments, Relive use or stored answers are protected by default.
  • Limits show how full each store is and what a limit means in time ("keeps ~24 h").
  • Call-status donut removed - it described traffic, not storage. Status split moves into the calls row breakdown.
  • Round 2: Space over time (stacked per day, forecast, disk-full date, next automatic cleanup) · Where the space goes (busiest endpoints with "Stop recording", largest single calls, cost per project across every store, repeated identical calls) · low-disk warning and automatic space guard · skip OPTIONS / health checks · pinned calls protected · 8 s Undo on every delete · sort the store list · Files & backup (data folder, -wal write-log size + fold in, integrity check, back up / restore .zip, nightly backup of your work).
  • Round 3 - Relive apart: Relive run recordings (session cycles with reliveRunId) are their own store and group, never counted or cleaned as your session cycles. Relive panel per cycle: run strip (pass/fail, starred), keep last N runs, delete runs but keep the cycle, delete passed / keep failed. Own limit in Automatic cleanup, own chip in Clean up, own Danger-zone row.
  • Round 6 - calls limits + cascade: both inbound and outbound have an optional "and at most N calls" next to their size share (inbound starts at today's 7,000); the row says which limit is reached first. Deleting an inbound call always deletes its DB statements, Redis commands, caught log lines and triage mark in the same step.
  • Round 7 - DB share fills first: the oldest calls lose their whole capture at once (statements, result rows, Redis commands, caught log lines - one deleteForCalls), never part of a call. The inbound call stays and is marked "DB data removed · storage limit" so it never looks like it ran no SQL. Statements and Redis share one limit, so a call cannot keep its statements but lose its Redis commands.
  • Small configuration stores (settings, profiles, redactions, interception) have Export only, no delete.
