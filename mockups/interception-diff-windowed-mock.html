MOCKUP — not the running app. Windowed rendering, scoped search, per-section copy.

A big body should cost what you can see, not what you have

The panel renders every line of both halves. Expanding a large response builds tens of thousands of DOM nodes to fill a 340px box that shows eighteen of them.

1 · Why it is slow

DOM nodes (one per token, since colouring)~190,000~250

The call view already fought this and won — json-flat-view windows past 2,000 lines. This panel is the same problem in a smaller box, and two panels can be open on one call (request and response), so it pays the cost twice.

2 · The same mechanism, simpler

Rows here are uniform height — no comment cards, no composer — so the offset table the flat view needs collapses to one multiplication. Two spacers hold the scrollbar honest and only the visible slice plus a little overscan is built.

copy: Response · Headers · Body. The first button is named after what it copies, so it says Request on the request panel and Diff when you are looking at the diff — which is how “copy the request only” and “copy the response only” are expressed: each half already has its own panel. One thing this removes

The “too large to colour” cap goes. It existed because colour costs one DOM node per token and this panel rendered every line; windowing is the real fix, so a 28,000-line body is now coloured like any other. Tokenizing one costs 45 ms — measured, and paid once on expand, not per keystroke.
