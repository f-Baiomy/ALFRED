MOCKUP — not the running app. Enabling and disabling one action inside a rule.

Turn one action off without deleting it

A rule you are iterating on often has an action you want to try WITHOUT, then bring back exactly as it was — swapping "reply with a mock" for "pause and edit by hand" and back, without retyping either one.

1 · The new control — a fourth icon, same row

Sits with ▲ ▼ ✕ rather than replacing any of them — moving, deleting and enabling/disabling are three different questions about the same action. A power icon rather than a checkbox: it reads as a switch at a glance in a row that already has three other icon buttons, and green-when-on avoids a second colour vocabulary.

1 Pause and wait for me (after the supplier answers) i
Wait up to 30 seconds If nobody answers: release it unchanged

2 · Disabled — dimmed, not hidden

The fields stay visible and editable. You are not deleting the action, you are asking the engine to skip it for now — so you can still fix a typo in a disabled action, or read what it would do, without switching it back on first. The whole card just reads as "this is not currently part of the rule."

1 Pause and wait for me (after the supplier answers) off i
Wait up to 30 seconds If nobody answers: release it unchanged
2 Reply with a different response i
Status 418 1 header

This is the case that motivated it: two actions that would otherwise conflict — a rule can only end a request once, and this pair does — sitting side by side, only one of them actually live. Toggle one off, toggle the other on, without deleting or retyping either.

3 · Disabling a condition disables everything inside it

One switch for the whole block. A condition's branches and their nested actions are not separately toggleable — turning the IF off is turning off the entire decision, exactly the way removing it would, except it is still there to turn back on. The nested action cards keep their own ▲▼✕ (you can still reorder or delete what is inside while the whole thing is off), just not their own power icon — there is nothing to independently enable inside a block that is not running at all.

1 Condition off i
IF match all of these
Request JSON field supplier contains "travelport"
then
1 Set JSON field in request body
passengers[*].count = 12

Neither this condition's branches nor the actions inside them run while it is off.

4 · The rules list already shows what a rule does — now it shows what it isn't doing too

A disabled action's chip goes dashed and struck through where an active one is solid — the same "still here, not in effect" language the paused-call editor already uses for a removed header. And a rule only reads "holds the caller" when a PAUSE action is actually switched on; a disabled one no longer earns that warning, since nothing is holding anybody.

Search debugging holds the caller
Pause response — wait 30s Reply with 418, 1 header priority 100

Only one pause/terminal action here is actually live, so the badge is accurate rather than warning about a caller nothing is holding.

5 · Dragging an action into a condition's scope

A drag handle (⠿), not the whole card — the card already holds clickable buttons and typed fields, and making the entire surface a drag source is exactly what fought text selection in the diff panel two fixes ago. Drop targets are every action list in the rule at once: the request lane, the response lane, every branch's then, every ELSE — so an action can move from top-level into a branch, out of a branch back to top-level, or from one branch straight into another.

⠿ 2 Set request header
1 Condition
IF match all of these
Request JSON field supplier contains "travelport"
then — drop here

Only a scope of the same phase lights up as a valid target while dragging — a response action cannot land inside an IF_REQUEST, the same rule the "+" buttons already enforce. The two levels of nesting the backend allows are the same limit here: a condition already two deep won't accept another one dropped into it.

What stays true regardless of on/off

A disabled action is still validated. If you leave a PAUSE_RESPONSE with no timeout while it is off, saving the rule still refuses it — so switching it back on later never surprises you with an error that was always there, just hidden. What DOES relax: the "two terminal actions" / "terminal and a pause" contradiction checks only count actions that are actually on — that pairing above is the reason this exists, and it would defeat the whole feature if turning one off still tripped the same complaint.

Default is on. Every action you have ever saved, and everything imported from a file, keeps working exactly as it does today — this is something you turn off, not something you turn on.
