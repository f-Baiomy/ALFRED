# Supplier integrations (proxy layer)

Alfred runs **two** mitmproxy services in `docker-compose.yml`, one per traffic direction — do not conflate them:

- **`proxy`** — regular (forward) proxy mode, port `127.0.0.2:443` (the default/shared listener), addon `proxy/log_and_route.py`. Logs **outbound** traffic: any HTTP/HTTPS-aware client that's been made proxy-aware (e.g. `http.proxyHost`/`http.proxyPort`/`https.proxyHost`/`https.proxyPort` JVM system properties, whether set at JVM startup or injected into an already-running JVM via the Attach API — see `wildfly-proxy-toggle/`) gets every call it makes logged, for whatever real hostname it actually calls. No hosts-file redirect, no special hostname convention.

  **Per-project outbound attribution** (opt-in, per project, via `settings.properties`'s `internal_call_services` optional 4th/5th fields — `name:listenPort:upstreamPort:outboundProxyHost[:outboundProxyPort]`) gives a project its own dedicated forward-proxy address so an outbound call can be tagged `service_name = <which project's listener accepted this connection>` instead of showing up as unattributed "External" traffic. Mirrors `reverse-proxy`'s per-project-port pattern exactly, just for the opposite direction: `proxy/forward-proxy-entrypoint.sh` turns each project's assigned internal container port into its own `--mode regular@<internalPort>` flag (`FORWARD_PROXY_PORT_MAP`, "name:internalPort" pairs — the internal port itself is a deterministic `start.py`/`restart.py`-assigned value, `20000 + that project's index in internal_call_services`, kept out of `docker-compose.yml` since Compose can't expand a variable-length list), alongside the always-present default listener above (so any proxy-aware client not part of this scheme keeps working exactly as before). `docker-compose.override.yml` then publishes each opted-in project's `outboundProxyHost:outboundProxyPort` (`outboundProxyPort` defaults to `443`) to that internal port, the same way it already publishes `reverse-proxy`'s per-project `listenPort`s — see `sync_compose_override()` in `start.py`/`restart.py`. `log_and_route.py` resolves `service_name` from `flow.client_conn.sockname`'s port (same technique `log_and_route_reverse.py`'s `_listen_port()` already uses) and only includes the key in the webhook payload when it resolves — a call on the default/shared port is never touched by any of this. A project that only lists `name:listenPort:upstreamPort` (the original 3-field format) simply gets no outbound attribution; the two features (inbound logging via `listenPort`, outbound attribution via `outboundProxyHost`) are independent per project and can be mixed freely in the same comma-separated value.
- **`reverse-proxy`** — reverse proxy mode, ONE mitmdump process holding one listener PER PROJECT, addon `proxy/log_and_route_reverse.py`. **Opt-in** — only started when the `inbound-logging` Compose profile is active (`COMPOSE_PROFILES=inbound-logging` in `.env`, set by `start.py`/`restart.py` from `settings.properties`'s `reverse_proxy_enabled`, false by default); many deployments only need OUTBOUND logging (the always-running `proxy` service) and have no inbound project to front, so this keeps an idle container from ever existing for them. Logs **inbound** traffic for any number of NAMED upstream projects, routed by **which port the request arrived on**: `REVERSE_PROXY_PORT_MAP`/`INTERNAL_CALL_SERVICES` (the same `.env` value, read by both `reverse-proxy` and `backend`, baked in by `start.py`/`restart.py` from `settings.properties`'s `internal_call_services`) is a `name:listenPort:upstreamPort` list, and `proxy/reverse-proxy-entrypoint.sh` turns each triple into its own `--mode reverse:http://<upstreamHost>:<upstreamPort>@<listenPort>` flag. **mitmproxy therefore does all the routing itself** — each listener has a fixed upstream, and the addon never touches a flow's destination; it only works out which project a flow belongs to (`flow.client_conn.sockname`, i.e. the arrival port) to label the call and honour that project's toggle. Callers swap `localhost:<upstreamPort>` for `localhost:<listenPort>`; each project keeps its own real port and needs no changes. A flow arriving on an unconfigured port (shouldn't happen — this process only listens on mapped ports) is labelled with the reserved name `"unknown"` rather than going unlabelled. **Logging is toggled per NAME independently, live, without restarting the container** — turning one project off never affects any other, or forwarding for any of them — via `toggle-wildfly-reverse-proxy.sh`/`.bat <name> [on|off]` (updates a `name=on`/`name=off` line in `proxy/reverse-proxy-enabled.flag`, re-read by mtime on every request) or the Settings page's per-project Enable/Disable buttons (`GET /internal-calls/services`, `POST /internal-calls/services/{name}/logging-enabled`, same flag file). Either way, **forwarding never stops** — only whether that name's calls get recorded does.

  Not to be confused with `wildfly-proxy-toggle/`'s Attach-API tool (see its own README) — that one makes an already-running WildFly JVM's **outbound** calls route through the *forward* `proxy` service; this section's toggle only controls logging on the *reverse* `reverse-proxy` service for **inbound** calls. Same repo, same word "proxy," opposite direction, unrelated mechanisms.

- **`keep_host_header=true` is still load-bearing** (set in `proxy/reverse-proxy-entrypoint.sh`), even though routing no longer reads the `Host` header. Without it, mitmproxy replaces the incoming `Host` with each listener's own upstream (`host.docker.internal:<upstreamPort>`), and any upstream that builds absolute URLs from `Host` then hands clients links straight to that address — unreachable from the client, and a bypass of this proxy where it does resolve (confirmed live: WildFly's `302 Location` became `http://host.docker.internal:8080/odeysysadmin/`; with the flag it correctly reads `http://localhost:9001/odeysysadmin/`). Same reason nginx reverse proxies send `proxy_set_header Host $host`. It also makes the client's own address available for the `original_url` field.

- **Why port-based and not hostname-based routing — three separate traps, all avoided by staying on `localhost`.** An earlier revision gave each project a hostname (`core-service.local`, pointed at `127.0.0.1` in the host's hosts file) behind one shared port. Each of these bit in turn: **(1) Browser session cookies.** A page served from `localhost:8500` calling `core-service.local:9000` is a *cross-site* request, so Chrome refuses to send a `SameSite=Lax` cookie (the default when the attribute is absent) — the app's `Set-Cookie` landed, no `Cookie` ever came back, and the app answered "Session has been expired" on every subsequent call. Unfixable without HTTPS (`SameSite=None` requires `Secure`) or a per-project dev-server proxy. **(2) mitmproxy rewrites `Host` before addon hooks run**, so a Host-header lookup only ever saw the `--mode` target and every project's traffic silently went to the fallback upstream. **(3) Docker Desktop leaks the host's hosts file into container DNS**, so `core-service.local` resolved to `127.0.0.1` *inside* a container — the container itself — and any container relaying to it (notably the forward `proxy`, when a proxied JVM calls another local project) got `ECONNREFUSED [Errno 111]`. Routing by arrival port sidesteps all three: same host (`localhost`) means same-site cookies, no `Host` header is consulted for anything, and no name resolution happens at all.

- **`docker-compose.override.yml` is generated, not hand-written.** `start.py`/`restart.py` write it (gitignored, auto-loaded by Compose) from `internal_call_services`, publishing `127.0.0.1:<listenPort>:<listenPort>` on `reverse-proxy` for each inbound-logging project, and `<outboundProxyHost>:<outboundProxyPort>:<internalPort>` on `proxy` for each outbound-attribution project (see `_forward_proxy_assignments()`/`sync_compose_override()`) — Compose can't expand a variable-length port list from an env var, so neither set of port publishes can live in `docker-compose.yml`. Rewritten on every run, and deleted entirely when no project uses either feature.

- **Neither addon rewrites a flow's destination.** In regular mode, `flow.request.host`/`pretty_url` already reflect the real destination the client asked for — via an HTTP `CONNECT` for HTTPS, or an absolute-URI request line for plain HTTP — so `log_and_route.py`'s `request()` hook just reads them into `call_log`. In reverse mode, each listener's upstream is fixed by its own `--mode reverse:` flag, so `log_and_route_reverse.py` doesn't need to (and deliberately doesn't) touch `flow.request.host`/`.port` either — an earlier revision that did was the source of several hard-to-diagnose failures. Both addons are pure observers of routing decided elsewhere.

- **Both addons persist nothing themselves, and log every call in two phases**, POSTing to their own backend webhook (`WEBHOOK_URL=http://backend:5000/calls/webhook` for `proxy`, `.../internal-calls/webhook` for `reverse-proxy` — two separate stores, see docs/architecture.md). `request()` POSTs `{WEBHOOK_URL}/prepare` **synchronously** (blocking mitmproxy's asyncio loop, bounded by `PREPARE_TIMEOUT_SECONDS`) to get a real call id back before the request is forwarded upstream — the one deliberate exception to "never block a hook" in these files, needed so `response()`/`error()` later know which call to complete. Those two then POST `{WEBHOOK_URL}/{id}/complete` the normal way: `_write()` is a non-blocking `queue.put_nowait()`, and a single daemon thread drains the queue and POSTs via stdlib `urllib.request`, swallowing (and logging) failures rather than raising. Stdlib-only deliberately — both run the stock `mitmproxy/mitmproxy` image, no Dockerfile/pip step. **`WEBHOOK_URL` is load-bearing**: if unset, backend is unreachable, or `prepare` times out, the call is proxied/forwarded correctly but never recorded anywhere (backend is the sole writer of call history) — and if `complete` alone fails to reach backend, the call stays visible there as in-progress indefinitely (an accepted gap, not auto-recovered).

- `prepare`'s payload includes `original_url` and `url`, plus method/headers/body/timestamp. For `proxy` (forward mode) these are always identical — kept as two fields only for backward compatibility with the existing `CallRecord` shape/frontend. For `reverse-proxy` they genuinely differ: `original_url` is what the client called (rebuilt from its own `Host` header, e.g. `http://localhost:9001/...`) and `url` is where that listener forwarded it (e.g. `http://host.docker.internal:8080/...`). Both are constructed by hand rather than read off `flow.request.pretty_url`, which reflects the `Host` header either way and so can never show the upstream. `complete`'s payload carries `duration_ms` plus either `response` or `error`. `log_and_route_reverse.py` additionally forwards `X-Request-Id`/`X-Session-ID`/`X-Operation-Id` request headers into the call record, reusing the frontend's own tagging convention.

- **Per-folder CA identity**: `proxy/certs/` holds a CA generated fresh on first container start, unique to that project checkout. Only one Alfred folder's CA can be trusted under the "mitmproxy" friendly name per OS/JDK truststore at a time — running `start.py` from a different folder re-syncs trust to that folder's CA.

- **A running JVM does not pick up truststore changes live** — restart the Java app after its JDK's cert import, unless you're injecting proxy properties into an already-running JVM specifically to avoid a restart, in which case make sure that JVM's JDK already trusted this CA *before* you started it.

## Host-side setup (Docker cannot touch the OS cert store)

- `setup.bat`/`setup.sh` are a **one-time, separate** step installing Docker/Python (`winget`/apt-dnf-yum/Homebrew) — they don't touch certs/containers.
- `start.py` (delegates to `start.ps1` via `certutil` or `start.sh` via `update-ca-certificates`/Keychain) does, in order: sync WildFly's port-offset (`sync-wildfly-port-offset.py`, only if `wildfly_port_offset_enabled`) → bake `settings.properties`'s `reverse_proxy_enabled`/`internal_call_services` into `.env` as `COMPOSE_PROFILES`/`REVERSE_PROXY_ENABLED`/`INTERNAL_CALL_SERVICES` and regenerate `docker-compose.override.yml` → `docker compose up -d --build` → resync CA into OS store → resync CA into every JDK in `jdks.txt` + current `JAVA_HOME`. If `reverse_proxy_enabled` was just turned off on an already-running deployment, also explicitly `docker compose stop reverse-proxy` (a plain `up` never stops a container that's fallen out of profile scope on its own). **The port-offset step is legacy/optional even when `reverse_proxy_enabled=true`, now that `reverse-proxy` takes its own `listenPort` per project rather than claiming a project's own port** — it's only relevant if you specifically want WildFly reachable on its *original* port number both proxied and unproxied at once; nothing requires it for inbound logging to work, just add WildFly to `internal_call_services` like any other project. The CA-trust steps are load-bearing - a client trusting this CA is what lets it get proxied HTTPS calls without cert errors. Safe to re-run; already-done steps are skipped. Both `start.py` and `restart.py` also accept `--wildfly-proxy [on|off]` (the outbound Attach-API toggle, `wildfly-proxy-toggle/`) — the old `--wildfly-reverse-proxy` flag is gone, since whether `reverse-proxy` runs at all is now `reverse_proxy_enabled` (deploy-time) and each project's logging is toggled independently at runtime instead of on every start/restart.
- `ensure_backend_port()` (in `start.py`/`restart.py`) probes port 5000 with a plain socket **without `SO_REUSEADDR`** — on Windows that flag would let the probe bind over an already-listening socket and falsely report "free". Skips the check if `.env` already exists or this project's own backend container is already up (avoids mistaking our own binding for a conflict). Otherwise walks upward in steps of 50 until free and writes `.env`.
- `deploy.py [service...]` = `git fetch` + hard-reset to `origin/<branch>`, then delegates to `restart.py` (forwarding `--wildfly-proxy` too).
- `stop.py` = detach the outbound Attach-API proxy, remove WildFly's port-offset (`sync-wildfly-port-offset.py --disable`), then `docker compose down --remove-orphans`.
- `frontend/.dockerignore` / `backend/.dockerignore` exist specifically to stop `node_modules`/module `target/` dirs from bloating the Docker build context on every rebuild — check these first if a build reports a suspiciously large context.
- `docker_storage_report.py` — standalone diagnostic/cleanup for Docker's own disk usage (images/containers/volumes/build cache/log sizes, plus WSL2 vhdx size on Windows) with an optional safe-cleanup pass (`--yes`/`--no-clean`/`--log-threshold-mb`/`--compact-vhdx`) — never touches volumes, so it can't lose call history.
