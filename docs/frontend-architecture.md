# Frontend architecture

Angular, standalone components + signals, no NgModules/NgRx.

**There is no polling anywhere in the app - every state service is fetch-on-demand, backed by a WebSocket that triggers the next fetch.** For calls/captured-calls, `createCallListView` (`core/state/call-list-view.ts`) fetches from the backend only: once on construction, whenever search/sort/supplier-filter/page-size changes (offset reset to 0), on `loadMore()` (next page, appended), and on `refresh()` (re-fetches offset 0 through however many are currently loaded, replacing them wholesale). `CallsStateService`/`SessionCycleDetailStateService` call `refresh()` the instant their `/ws/calls` socket receives a push, instead of a timer eventually picking it up - a call arriving during a reconnect gap is only surfaced by the next push or a manual refresh, an accepted trade-off (no periodic fallback). A small `liveCalls` buffer per state service still shows a just-pushed call instantly (deduped by `callKey` against what's loaded) while that `refresh()` is in flight. `matchingCalls`/`stats`/`supplierOptions`/`groupedCalls`/"select all" are therefore scoped to *what's been loaded so far*, not the true backend total - `remainingCount` (`total - loaded`) is what drives the "Load N more" button and is the only place the true total is known. `SessionCycleDetailStateService` additionally keeps a `capturedByKey` map (content-keyed by `callKey`) alongside every fetched page, since a live WebSocket push only carries the bare `CallRecord` - removal needs the wrapper `CapturedCall`'s real backend id, which only exists once a fetch has confirmed it.

**Session-cycles' and profiles' own lists (not their calls) follow the same fetch-on-demand shape via two more WebSocket endpoints, `/ws/session-cycles` and `/ws/profiles`.** These carry no payload (`{"type":"session-cycles-changed"}`/`{"type":"profiles-changed"}`) - a cycle create/rename/record/pause/delete or a profile create/update/delete is rare and the whole list is cheap to refetch, so `SessionCyclesStateService`/`ProfilesStateService` just treat any message as "refetch now" rather than merging/deduping individual records. Each has its own `SessionCycleEventsWebSocketHandler`/`WebSocketSessionCycleNotificationAdapter` (and profiles' equivalents) - duplicated per-slice rather than shared with `backend-calls`' `CallEventsWebSocketHandler`, since each slice's WebSocket infrastructure is meant to be self-contained (no new cross-slice dependency for this). One gotcha hit live: Spring names a `@Component`/`@Configuration` bean from its simple class name regardless of package, so three same-named `WebSocketConfig` classes across `backend-calls`/`backend-session-cycles`/`backend-profiles` collided at startup (`ConflictingBeanDefinitionException`) - the two newer ones are named `SessionCyclesWebSocketConfig`/`ProfilesWebSocketConfig` instead. `@EnableWebSocket` only needs to appear once anywhere in the context to activate the feature app-wide, but each module's config class repeats it anyway so it doesn't silently depend on another module's copy still being present. Local mutations already trigger their own immediate refetch via each service's existing `refreshNow()`/`tap()` calls - the WebSocket's job is purely to catch changes made by *other* clients (multi-tab, multi-user).

**A call's request/response is fetched only once its card is actually expanded, via `CallCardComponent`'s `detailState` (`'collapsed' | 'pending' | 'loading' | 'loaded' | 'error'`) - the list only ever has `CallSummary` data (see docs/architecture.md).** `CALL_LIST_CONTROLS_STATE.getCallDetail(callId)` is what each concrete state exposes to get there - `CallsStateService` hits `GET /calls/{id}/detail`, `SessionCycleDetailStateService` hits the session-cycles equivalent - so `CallCardComponent`/`CallActionsComponent`/`BulkActionsBarComponent` never need to know which context they're in. An individual "Show request/response" click fetches immediately; a bulk "Expand all" instead marks every card `'pending'` and lets each one's own `IntersectionObserver` (`rootMargin: '200px'`) gate the actual fetch until it scrolls into view, so expanding a 150-call list doesn't fire 150 requests at once. **The IntersectionObserver must only ever promote an already-`'pending'` card into `'loading'`, never a `'collapsed'` one** - confirmed live: an earlier version's guard allowed `'collapsed'` too, which meant any card merely visible on page load silently fetched its detail with no click at all, defeating the entire point. `call-card.component.spec.ts` mocks the global `IntersectionObserver` to lock this in as a regression test, since Karma's headless fixture layout doesn't naturally reproduce it.

**`getCallDetail(callId)` always makes a real network request - there is deliberately no client-side detail cache, not even for the same call id within one session.** An earlier version had a root-provided `CallDetailCacheService` shared across the dashboard and every session-cycle page; export and duplicate-to-cycles hydration (below) populated it for every call they touched, and `CallCardComponent` separately checked it on construction to auto-promote a card straight to `'loaded'` on a hit. That meant exporting or duplicating a whole cycle's calls silently pre-loaded the cache for all of them, and simply (re)opening that cycle's page afterward rendered every card already fully expanded (bodies parsed, every `JsonPanelComponent` + its comments constructed at once) with zero clicks - reproducing the original eager-load problem via the cache instead of the network. The cache was removed outright rather than patched, per an explicit requirement that detail must always be lazy-loaded on expand, even if it was already loaded before (this session or otherwise) - a card that's re-expanded, or a second card for the same call id, always issues a fresh request.

**`CallRecord.supplierName` (a highlighted `.supplier-badge` on `CallCardComponent`, hidden entirely when absent) is part of the summary, not the detail** - it's server-computed from the request body (see `CallSummary.supplierNameOf` in docs/architecture.md) before the body itself is ever sent to the frontend, so it shows on a collapsed card with zero extra requests, unlike everything else in `request`/`response`.

**Every action that needs a call's full data - `CallActionsComponent` (cURL/JSON/report), `BulkActionsBarComponent` (bulk cURL/report/JSON/duplicate-to-cycles) - hydrates first, regardless of whether the card is expanded.** A selected/acted-on call may only be a `CallSummary` if it was never expanded, and no-truncation is a hard requirement for every export path; each hydrates via the same `getCallDetail()` path - always a real fetch, even if this same call was hydrated by an earlier action - merging the result onto the summary (`{...call, ...detail}`) before building anything. Bulk actions hydrate the whole selection concurrently via `forkJoin`, not sequentially.

**Six components are shared verbatim between the dashboard and session-cycle detail pages via DI tokens**, not forked: `CallCardComponent`, `BulkActionsBarComponent`, `HeaderComponent`, `StatsBarComponent`, `CallListComponent`, `JsonPanelComponent`. `core/state/call-selection.tokens.ts` defines the four interfaces (`CallSelectionState`, `BulkSelectionState`, `CallListControlsState`, `CallRemovalState`); `appConfig.ts` points the first three at `CallsStateService` app-wide, `SessionCycleDetailComponent` overrides all four locally via component `providers`.

**Backend URL is resolved per-deployment** (`AppConfigService` reads `window.BACKEND_URL`, generated into `env.js` at container start from `BACKEND_PORT`) — never hardcode `localhost:5000`, since that means the *viewer's* machine, not the server's.

**Three hot-path derivations are memoized in `WeakMap`s** keyed by the (immutable, `readonly`-field) `CallRecord` object in `shared/utils/call-utils.ts`: `callKey`, `supplierOf`, `callTime`. Safe because every fetch parses fresh objects and a `WeakMap` entry is reclaimed once that fetch's object is dropped — no eviction logic needed. (Search itself - `matchesSearch`/`searchHaystack` - moved server-side along with the rest of filtering/sorting/pagination; see docs/architecture.md.)

**JSON is never rendered via `innerHTML`** — tokenized (`shared/utils/json-tokenizer.ts`) and rendered through template interpolation or the recursive `json-tree` component.

**Past `WINDOWING_LINE_THRESHOLD` (2000) lines, `JsonFlatViewComponent` renders only the rows near the viewport**, with a `.code-spacer` above and below standing in for the rest. Measured on a real 640KB Amadeus SOAP body: rendering all 28,937 lines cost 186,734 DOM nodes and blocked the main thread for 4,098ms to show the ~20 rows that fit in the 380px box; windowed it is 230 nodes and 461ms, of which ~166ms is fetching/pretty-printing/tokenizing the body and is unrelated to rendering. Parsing was never the bottleneck (XML parse + pretty-print + tokenize + line-split measured 117ms total), so **a Web Worker would buy nothing here** — the cost was node creation plus layout. Rows are *not* uniform height (a line can carry comment cards and an open composer), so this keeps its own prefix-sum offset table rather than using CDK's fixed-size virtual scroll, which assumes one height per item. Consequences to respect when touching it: the line and comment-card heights are pinned in `.code-lines.windowed` in `styles.scss` and mirrored as constants in the component — **change one and you must change the other** — while the comment composer is deliberately *measured* at runtime instead, because its height depends on the theme's font and button padding (pinning it to a guessed 92px squashed a control that needs 102px, and with `overflow: visible` its textarea and buttons spilled out over the surrounding code lines); all of them must keep `box-sizing: border-box` with no vertical margins, since `offsetHeight` excludes margins and the default `0.15rem`/`0.5rem` measured a 10px-per-open-composer drift between content and scrollbar; the windowed `plain` variant switches from `pre-wrap` to `pre`, since a wrapped line's height can't be known in advance; and `JsonPanelComponent`'s jump-to-match resolves the active match's row from `displayLines()` rather than `querySelectorAll('mark.hl')`, because a match further down the body has never been rendered. Below the threshold none of this applies — the markup and behaviour are exactly what they always were. Exports and Copy are unaffected either way: they read `baseText()`, never the DOM, so the never-truncate rule holds regardless of what's on screen.

**Comments** are identified by `(callId, block, lineIndex)` against the *unfiltered* pretty-printed text, so "Lines only" filtering can never shift a comment onto the wrong line. `callId` here is always `call.id` (the backend-assigned UUID, see docs/architecture.md), never `callKey()` (the content-hash used for selection/pins/trackBy/dedup) - every call site that reads/writes/lists comments (`JsonPanelComponent`'s `callId` input as wired from `CallCardComponent`, `CallActionsComponent`/`BulkActionsBarComponent`'s comment fetches for export, `commentsByCallId` maps passed into the export builders) passes `call.id`. Mixing the two would silently split a call's comments across two different keys. They sync live across tabs via `BroadcastChannel` (incoming broadcasts never re-broadcast, or tabs would echo forever). Loading is lazy for free, not via any special-cased logic: `JsonPanelComponent.ensureLoaded()` already ran in its constructor, but a card's four `JsonPanelComponent`s are only ever constructed once `detailState() === 'loaded'` (see above) - gating the panels' existence behind that state was enough on its own to stop the previous eager "fetch comments for every visible call's every block on render" pattern, with zero changes to `CommentsStore` itself.

**Theming** is one `data-theme` attribute + one CSS variable block per theme (`ThemeService`, `localStorage['alfred-theme']`) — no component branches on theme. Custom popovers (`EmojiPickerComponent`, `SelectPickerComponent`) use `position: fixed` computed via `shared/utils/popover-position.ts`'s `computeFixedPanelPosition()`, which walks up for the nearest CSS-Transforms-spec containing-block ancestor (`backdrop-filter`/`transform`/etc.) rather than assuming the viewport — needed because `header`/`.tab-nav` set `backdrop-filter` for glass themes.

**No export path (`.md`/`.json`/`.html`/cURL) ever truncates or summarizes call data** — a hard correctness requirement; test coverage in `*-builder.spec.ts` asserts on large generated bodies specifically to guard this.

**Every `<details>` in an HTML export (`html-builder.ts`) renders closed, never `open`** — the per-call wrapper in a bulk export and all four Headers/Body blocks in both single and bulk export - so opening the file shows a scannable list first, not every call and every block already expanded. Markdown's per-call `<details open>` wrapper is unaffected (a different, additive design: Markdown's collapsible sections are for de-cluttering a long scroll, not the reader's first view of the doc), only HTML's is collapsed by default.

**Every clipboard copy goes through `shared/utils/clipboard.ts`'s `copyToClipboard()`**, not `navigator.clipboard.writeText` directly — that API requires a secure context, which a plain-HTTP LAN deployment isn't; it falls back to `document.execCommand('copy')`.

**Four top-level routes/tabs** (`app.routes.ts`, nav in `layout/main-layout/`): Live Calls (`''`), Session Cycles (`cycles`, `cycles/:id`), Profiles (`profiles`), Settings (`settings`). There's no separate "Internal Calls" tab — inbound (frontend→WildFly) traffic is a **source filter inside the existing Live Calls dashboard** instead: `CallSource = 'external' | 'internal' | 'both'` (`core/models/call.model.ts`), switched via a picker in `HeaderComponent` (dashboard-only). `CallsStateService.setCallSource()` swaps which backend endpoint pair (`/calls` vs `/internal-calls`, REST + WebSocket) feeds the same `CallCardComponent`/`CallListComponent` — no forked UI for the second traffic direction, just a different data source behind the shared components (see docs/architecture.md for `backend-internal-calls`).

**Settings (`pages/settings/`)** has three partitions, tab-switched by a local signal — three genuinely different concerns sharing one page, not one feature:
- **Call filtering** (default) — accept-all/accept-only mode plus a host whitelist/blacklist (`CallFilterSettingsStateService` → backend's `backend-settings` slice). Controls which *outbound* supplier calls get logged in the first place, upstream of everything else in this doc.
- **Database** — read-only storage stats (per-store row counts/sizes) plus destructive "Clear all calls"/"Clear all cycles" actions, gated behind `ConfirmDialogService`.
- **Inbound logging** — only rendered if `InternalLoggingApiService`'s `getFeatureEnabled()` (the deploy-time `reverse_proxy_enabled` flag, `GET /internal-calls/feature-enabled`, fetched once) resolves true; many deployments only need outbound logging and hide this panel entirely. When enabled, lists every project from `settings.properties`'s `internal_call_services` (plus a reserved `unknown` row), showing each one's `localhost:<listenPort> → <upstreamPort>` mapping with its own Enable/Disable button via `getServices()`/`setEnabled(name, enabled)` (`GET /internal-calls/services`, `POST /internal-calls/services/{name}/logging-enabled`) — mirroring `toggle-wildfly-reverse-proxy.sh`/`.bat <name>`. Flipping one project never affects any other, or whether calls still reach its upstream, only whether that project's calls are recorded (see docs/supplier-integrations.md).

**`pages/json-view/`** is a fifth route (`/view`, deliberately outside the tab layout, opened via `window.open`) that reopens `JsonPanelComponent` full-page for one stored call block — a "pop out this JSON" affordance, not a new feature surface.

**Each level of nesting has its own hue** — `depthTintClass` returns `depth-tint-0..3` (cycling every four), and those classes set a `--depth-color` custom property that the waterfall rail, the nested view's children rail, and a sandwich card's two bands all read. It exists because `depthRailPx` caps indenting at `MAX_INDENT_LEVELS`, so past that point two different depths were drawn at the same x and a chain of callers could only be counted by eye. **Green, amber and red are deliberately not in the ramp**: they mean status and duration everywhere else in Alfred, so a level-2 rail in green would read as a health signal. In the nested view the tint rides on the `app-call-tree-node` host, so a card inherits its level without being told its depth and a nested node re-sets it for its own subtree; the *rail* takes `depth + 1`, since it introduces the level below rather than describing the card it hangs off. **A waterfall row draws one guide line per ancestor level plus its own** (`depthRails`), ancestors at 26% and its own at 90%, because a single line at the row's own indent says how far in a call sits but nothing about what it sits inside — a depth-2 row was one short tick floating in space, with nothing beside it for its hue to be read against. The lines are added *inside* the indent `depthRailPx` already reserved, so nothing moves; past `MAX_INDENT_LEVELS` the ancestors run out of room but the last line still carries the row's own level, or depth 4 would be drawn as depth 3. The nested view needs none of this — its ancestors are literally the cards around it. The tint lands on the bands' background rather than the card's border because `.call`'s border-color and box-shadow are already spoken for by selected/pinned/error/warning states.

**In the two tree views, selecting a call selects everything nested under it, and the checkbox is tri-state.** `CallSelectionState.setSubtreeSelected`/`subtreeSelection` are the whole surface; `call-tree.ts`'s `indexDescendants` supplies the subtree, and `subtreeSelectionOf` in `call-utils.ts` is shared by both concrete states so a half-filled box can't mean two different things on the dashboard and in a session cycle. The flat view deliberately keeps plain `toggleSelected` — it draws no hierarchy, so a half-filled box there would refer to nothing on screen. A parent stays selected in its own right after a child is unticked (it's still a call, and still exports); 'some' is what makes that visible instead of the box overclaiming. Clicking a half-filled parent *fills* it. Drag-paint latches subtree mode at `startDragSelect` rather than asking each card, so one drag can't be half one rule and half the other. **The reason any of this needed writing is that the nested view was already selecting — upwards.** `mousedown` bubbles, and nested cards are literally inside one another, so every ancestor card ran `CallCardComponent`'s host listener too: measured on a real trace, pressing one supplier call at depth 2 selected three calls, itself plus its parent plus its grandparent. The fix is one `stopPropagation`, and it is load-bearing — without it the subtree rules above are applied to the wrong calls.

**Folding is per-call-id, shared by both tree views, and deliberately not persisted.** `CallListView.foldedIds`/`setFolded`/`foldAll`/`unfoldAll` — nothing to do with the neighbouring `expanded`/`collapseAllVersion`, which are about a card's own Headers/Body panels; this hides a parent's *children*, not its payload. Folding a parent takes every foldable call under it along, so reopening returns one level instead of however many were open before — on a deep trace, restoring the whole subtree in one click undoes the entire point of having folded it. Unfolding touches only the one call. Folding never changes selection, and a folded parent still reads half-filled if something inside it is ticked, so hidden calls can't silently ride along into an export unnoticed. Only calls with children are ever put in the set (`foldableIds`), since folding a leaf is a no-op that `unfoldAll` would then have to clean up. The waterfall keeps a folded group's opening/closing bracket — it carries the timing — and drops only what sat between the halves: on a live 14-call trace, fold-all took 18 rows to 5. It is not persisted because the set describes one particular page of loaded calls; restoring it against a different page would fold calls the user never folded.

**An internal call is bracketed into a `request` half and a `response` half exactly when the call tree gives it children — one rule, everywhere.** The flat list gets there via `call-utils.ts`'s `computeSplitCallIds`, each export format via its own line-for-line mirror of it (`html-builder.ts`/`markdown-builder.ts`/`bulk-json-builder.ts`, per this codebase's mirror-per-consumer convention), and the nested/waterfall views via `call-tree.ts`'s `buildCallTree`; all four ask the same two questions of a candidate — is it strictly contained in the call's window, and is it attributable to that call (`passesOwnershipCheck`) — and hand a candidate contained by several calls to the innermost of them, vetoing only owners that merely *overlap*. There used to be a third question: a call whose surviving set was a single child had to clear a "blocking signature" (that child covering ≥30% of the parent and ending within its tail window) before the nesting counted. It was meant to reject coincidental containment, and it instead **silently desynchronised the exports from the waterfall** — a 24.84s odeysys call with one 2.86s core-service call inside it (11.5% coverage) came out of every export as a single unbracketed block, with its four supplier calls dumped after it instead of inside it, while the waterfall bracketed it correctly. The 11.5% was the *finding* about that call — odeysys spent 80% of itself before issuing a request — not grounds for flattening its structure. Keep the four implementations answering identically; when they diverge, an export stops matching the screen it was taken from, which is the one thing an export cannot do.

**Call diagnostics (`shared/utils/call-diagnostics.ts` + `components/call-diagnostics/`)** answer "where did this call's time actually go", which a waterfall cannot: a waterfall shows how long each call took, but the time *between* calls is whitespace, and on real traffic the whitespace is most of the request. `analyzeCall` assigns every millisecond of a root to exactly one bucket — `duration = setup + upstream + between + tail`. **`upstream` is the UNION of the children's windows, not their sum**: calls running in parallel occupy one stretch of wall clock, and summing them would claim more time than the request took. That union is also what makes "time between calls" well-defined when calls overlap — rather than n² per-pair gaps that can go negative, `between` is time inside the fan-out window with nothing in flight, which degenerates to the obvious gap when calls are sequential. Direct children only: a grandchild happened inside a child, so it belongs to that child's accounting, and mixing depths would double-count — which is also why **every call with children gets its own panel, at any depth**, rather than only the root. `analyzeCall` was always depth-agnostic; the waterfall's row builder was gating it on `depth === 0`, which hid the breakdown for the call you usually want it for — the service in the middle that actually did the fanning out. On a live trace the root reads "74% of this call runs before the first request goes out" while the `core-service` call inside it reads "76% of this call is spent waiting upstream": two different diagnoses of two different calls, and only the second one points at the suppliers. **Nothing renders one until a `diagnose` button is pressed**, and the panel then opens *attached* to the call it describes: in the waterfall, directly above that call's own row with a shared edge (`.waterfall-diag` zeroes `.diag`'s top margin and `.waterfall-row-diag` drops the row's top border, so the two read as one block); in the nested view, as the first child of the card itself, above the request band. With several calls in a trace able to show a breakdown, a gap would leave it ambiguous which row a panel belongs to. The nested view gets the panel by **projection** (`[callDiagnostics]`) rather than building it in `CallCardComponent`: only `CallTreeNodeComponent` holds a `CallTreeNode`, and gating the projection on the open state means a page of parents costs no `analyzeCall` until one is actually asked. The button sits at the far right of a waterfall row (where the old always-on `▼ diagnose` label was) but with the other per-call actions on a nested card — that band's right edge is the request/response marker and the timestamp after it already wraps to its own line, so a button out there reads as belonging to the date. Per call it derives **slack** (how much slower this call could get before the total moves) and hence the critical path — on a measured live trace only 1 of 5 calls had zero slack, so optimising the other four would have changed nothing. The findings engine reports the dominant phase, sequential fan-out (what an `await` in a loop looks like: nothing overlaps and the total jumps without any one call slowing down), failures, and healthy parallelism. **Duplicate detection never claims two requests are identical from method and url alone** — `analyzeCall` only returns *candidates* (same method, same full url, within 150ms) and `CallDiagnosticsComponent.confirmDuplicates` fetches both request bodies and compares them before saying anything. That distinction is not academic: on real traffic two calls to one `FlightSearch` endpoint 27ms apart carried `{"supplier":"Galileo"}` and `{"supplier":"TravelportNdc"}` — a legitimate two-supplier fan-out that the url-only rule called duplicated work. Bodies aren't in the list payload, hence the fetch; it happens only on expand and only for calls that already match, and if a fetch fails nothing is claimed. Headers are deliberately excluded from the comparison — they routinely carry a per-request id or a freshly signed token, so genuinely duplicated calls would differ there and the check would never fire.

**Per-call network phases come from the proxy** (`proxy/log_and_route.py`'s `_phase_timing` → nullable columns on `call_metadata` → `CallSummary.timing`), and answer *why* a call was slow rather than just that it was. Two non-obvious properties: **connect and TLS happen INSIDE the time-to-first-byte window**, not before it, because mitmproxy opens the upstream connection lazily — rendered as four consecutive segments they summed to 328ms for a call that took 196.62ms, so `CallDiagnosticsComponent.phases` subtracts the handshake out of `ttfb` to leave the upstream's own think time. And mitmproxy **reuses** connections, so `connect_ms`/`tls_ms` are only reported when the handshake actually happened during that request — their *presence* is the finding, since paying for a handshake on every call means connections aren't being pooled. Null anywhere means NOT MEASURED, never zero; a call logged before this existed must not read as "measured, and instant". `CallTiming.isEmpty` needs `@JsonIgnore` — Jackson treats any `isX()` on a record as a property and was serializing an extra `"empty": false` onto every call in every list response.

**`GET /calls/baseline` / `GET /internal-calls/baseline`** give one endpoint's `sampleSize`/p50/p95 so a duration can be judged rather than read. Scoped to the exact url (the same path against two suppliers are different endpoints), COMPLETED calls only (a failure's duration measures how long it took to fail), fetched lazily on panel expand — with the list it would fire one aggregate query per row — and against whichever store the call came from, since inbound roots aren't in `calls.db`. `sampleSize` is part of the answer: under five calls the panel says how few there are rather than presenting a percentile of three as a baseline.
