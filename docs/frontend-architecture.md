# Frontend architecture

Angular, standalone components + signals, no NgModules/NgRx.

**There is no polling anywhere in the app - every state service is fetch-on-demand, backed by a WebSocket that triggers the next fetch.** For calls/captured-calls, `createCallListView` (`core/state/call-list-view.ts`) fetches from the backend only: once on construction, whenever search/sort/supplier-filter/page-size changes (offset reset to 0), on `loadMore()` (next page, appended), and on `refresh()` (re-fetches offset 0 through however many are currently loaded, replacing them wholesale). `CallsStateService`/`SessionCycleDetailStateService` call `refresh()` the instant their `/ws/calls` socket receives a push, instead of a timer eventually picking it up - and again the instant the socket RECONNECTS, since a call logged while it was away is never pushed to that client at all and would otherwise stay invisible until the next unrelated call happened to arrive.

**Every socket in the app is opened through `reconnectingSocket` (`core/state/reconnecting-socket.ts`), never `webSocket()` directly - `retry` alone is not enough and this is not a style preference.** RxJS's `webSocket` only *errors* on an abnormal close (code 1006 - a crash, a dropped network); a *clean* close (1000/1001, which is what a graceful backend restart or redeploy sends) makes it *complete* instead, and `retry` ignores completion. Every one of the five sockets therefore used to end its subscription silently - no error, nothing in the console - and that screen stayed deaf until somebody reloaded the page, which is how intercepted calls came to "stop notifying" Live Calls and Session Cycles. Confirmed live: closing `/ws/calls` with code 1000 froze the dashboard permanently while its sibling `/ws/internal-calls` socket kept working. `reconnectingSocket` pairs `repeat` with `retry` so both endings reconnect, and calls back on every open except the first so the caller can re-fetch what it missed. A small `liveCalls` buffer per state service still shows a just-pushed call instantly (deduped by `callKey` against what's loaded) while that `refresh()` is in flight. `matchingCalls`/`stats`/`supplierOptions`/`groupedCalls`/"select all" are therefore scoped to *what's been loaded so far*, not the true backend total - `remainingCount` (`total - loaded`) is what drives the "Load N more" button and is the only place the true total is known. `SessionCycleDetailStateService` additionally keeps a `capturedByKey` map (content-keyed by `callKey`) alongside every fetched page, since a live WebSocket push only carries the bare `CallRecord` - removal needs the wrapper `CapturedCall`'s real backend id, which only exists once a fetch has confirmed it.

**Session-cycles' and profiles' own lists (not their calls) follow the same fetch-on-demand shape via two more WebSocket endpoints, `/ws/session-cycles` and `/ws/profiles`.** These carry no payload (`{"type":"session-cycles-changed"}`/`{"type":"profiles-changed"}`) - a cycle create/rename/record/pause/delete or a profile create/update/delete is rare and the whole list is cheap to refetch, so `SessionCyclesStateService`/`ProfilesStateService` just treat any message as "refetch now" rather than merging/deduping individual records. Each has its own `SessionCycleEventsWebSocketHandler`/`WebSocketSessionCycleNotificationAdapter` (and profiles' equivalents) - duplicated per-slice rather than shared with `backend-calls`' `CallEventsWebSocketHandler`, since each slice's WebSocket infrastructure is meant to be self-contained (no new cross-slice dependency for this). One gotcha hit live: Spring names a `@Component`/`@Configuration` bean from its simple class name regardless of package, so three same-named `WebSocketConfig` classes across `backend-calls`/`backend-session-cycles`/`backend-profiles` collided at startup (`ConflictingBeanDefinitionException`) - the two newer ones are named `SessionCyclesWebSocketConfig`/`ProfilesWebSocketConfig` instead. `@EnableWebSocket` only needs to appear once anywhere in the context to activate the feature app-wide, but each module's config class repeats it anyway so it doesn't silently depend on another module's copy still being present. Local mutations already trigger their own immediate refetch via each service's existing `refreshNow()`/`tap()` calls - the WebSocket's job is purely to catch changes made by *other* clients (multi-tab, multi-user).

**A call's request/response is fetched only once its card is actually expanded, via `CallCardComponent`'s `detailState` (`'collapsed' | 'pending' | 'loading' | 'loaded' | 'error'`) - the list only ever has `CallSummary` data (see docs/architecture.md).** `CALL_LIST_CONTROLS_STATE.getCallDetail(callId)` is what each concrete state exposes to get there - `CallsStateService` hits `GET /calls/{id}/detail`, `SessionCycleDetailStateService` hits the session-cycles equivalent - so `CallCardComponent`/`CallActionsComponent`/`BulkActionsBarComponent` never need to know which context they're in. An individual "Show request/response" click fetches immediately; a bulk "Expand all" instead marks every card `'pending'` and lets each one's own `IntersectionObserver` (`rootMargin: '200px'`) gate the actual fetch until it scrolls into view, so expanding a 150-call list doesn't fire 150 requests at once. **The IntersectionObserver must only ever promote an already-`'pending'` card into `'loading'`, never a `'collapsed'` one** - confirmed live: an earlier version's guard allowed `'collapsed'` too, which meant any card merely visible on page load silently fetched its detail with no click at all, defeating the entire point. `call-card.component.spec.ts` mocks the global `IntersectionObserver` to lock this in as a regression test, since Karma's headless fixture layout doesn't naturally reproduce it.

**`getCallDetail(callId)` always makes a real network request - there is deliberately no client-side detail cache, not even for the same call id within one session.** An earlier version had a root-provided `CallDetailCacheService` shared across the dashboard and every session-cycle page; export and duplicate-to-cycles hydration (below) populated it for every call they touched, and `CallCardComponent` separately checked it on construction to auto-promote a card straight to `'loaded'` on a hit. That meant exporting or duplicating a whole cycle's calls silently pre-loaded the cache for all of them, and simply (re)opening that cycle's page afterward rendered every card already fully expanded (bodies parsed, every `JsonPanelComponent` + its comments constructed at once) with zero clicks - reproducing the original eager-load problem via the cache instead of the network. The cache was removed outright rather than patched, per an explicit requirement that detail must always be lazy-loaded on expand, even if it was already loaded before (this session or otherwise) - a card that's re-expanded, or a second card for the same call id, always issues a fresh request.

**`CallRecord.supplierName` (a highlighted `.supplier-badge` on `CallCardComponent`, hidden entirely when absent) is part of the summary, not the detail** - it's server-computed from the request body (see `CallSummary.supplierNameOf` in docs/architecture.md) before the body itself is ever sent to the frontend, so it shows on a collapsed card with zero extra requests, unlike everything else in `request`/`response`.

**Every action that needs a call's full data - `CallActionsComponent` (cURL/JSON/report), `BulkActionsBarComponent` (bulk cURL/report/JSON/duplicate-to-cycles) - hydrates first, regardless of whether the card is expanded.** A selected/acted-on call may only be a `CallSummary` if it was never expanded, and no-truncation is a hard requirement for every export path; each hydrates via the same `getCallDetail()` path - always a real fetch, even if this same call was hydrated by an earlier action - merging the result onto the summary (`{...call, ...detail}`) before building anything. Bulk actions hydrate the whole selection concurrently via `forkJoin`, not sequentially.

**Six components are shared verbatim between the dashboard and session-cycle detail pages via DI tokens**, not forked: `CallCardComponent`, `BulkActionsBarComponent`, `HeaderComponent`, `StatsBarComponent`, `CallListComponent`, `JsonPanelComponent`. `core/state/call-selection.tokens.ts` defines the four interfaces (`CallSelectionState`, `BulkSelectionState`, `CallListControlsState`, `CallRemovalState`); `appConfig.ts` points the first three at `CallsStateService` app-wide, `SessionCycleDetailComponent` overrides all four locally via component `providers`.

**Backend URL is resolved per-deployment** (`AppConfigService` reads `window.BACKEND_URL`, generated into `env.js` at container start from `BACKEND_PORT`) — never hardcode `localhost:5000`, since that means the *viewer's* machine, not the server's.

**Three hot-path derivations are memoized in `WeakMap`s** keyed by the (immutable, `readonly`-field) `CallRecord` object in `shared/utils/call-utils.ts`: `callKey`, `supplierOf`, `callTime`. Safe because every fetch parses fresh objects and a `WeakMap` entry is reclaimed once that fetch's object is dropped — no eviction logic needed. (Search itself - `matchesSearch`/`searchHaystack` - moved server-side along with the rest of filtering/sorting/pagination; see docs/architecture.md.)

**JSON is never rendered via `innerHTML`** — tokenized (`shared/utils/json-tokenizer.ts`) and rendered through template interpolation or the recursive `json-tree` component.

**Past `WINDOWING_LINE_THRESHOLD` (2000) lines, `JsonFlatViewComponent` renders only the rows near the viewport**, with a `.code-spacer` above and below standing in for the rest. Measured on a real 640KB Amadeus SOAP body: rendering all 28,937 lines cost 186,734 DOM nodes and blocked the main thread for 4,098ms to show the ~20 rows that fit in the 380px box; windowed it is 230 nodes and 461ms, of which ~166ms is fetching/pretty-printing/tokenizing the body and is unrelated to rendering. Parsing was never the bottleneck (XML parse + pretty-print + tokenize + line-split measured 117ms total), so **a Web Worker would buy nothing here** — the cost was node creation plus layout. Rows are *not* uniform height (a line can carry comment cards and an open composer), so this keeps its own prefix-sum offset table rather than using CDK's fixed-size virtual scroll, which assumes one height per item. Consequences to respect when touching it: the line and comment-card heights are pinned in `.code-lines.windowed` in `styles.scss` and mirrored as constants in the component — **change one and you must change the other** — while the comment composer is deliberately *measured* at runtime instead, because its height depends on the theme's font and button padding (pinning it to a guessed 92px squashed a control that needs 102px, and with `overflow: visible` its textarea and buttons spilled out over the surrounding code lines); all of them must keep `box-sizing: border-box` with no vertical margins, since `offsetHeight` excludes margins and the default `0.15rem`/`0.5rem` measured a 10px-per-open-composer drift between content and scrollbar; the windowed `plain` variant switches from `pre-wrap` to `pre`, since a wrapped line's height can't be known in advance; and `JsonPanelComponent`'s jump-to-match resolves the active match's row from `displayLines()` rather than `querySelectorAll('mark.hl')`, because a match further down the body has never been rendered. Below the threshold none of this applies — the markup and behaviour are exactly what they always were. Exports and Copy are unaffected either way: they read `baseText()`, never the DOM, so the never-truncate rule holds regardless of what's on screen.

**The call list builds a card only when its row scrolls into view (`@defer (on viewport)` in `call-list.component.html`) — the page size no longer decides whether the list is usable.** Constructing one `CallCardComponent` costs ~8ms, so a page of them was paid as a single main-thread block: measured on a real page, 400 rows = **one 3,226ms block** in the flat view and 3,501ms in nested, during which the browser cannot paint at all — which is exactly why cards appeared half-drawn or blank rather than merely slow. Scaling was *worse* than linear (100 rows 210ms, 200 rows 850ms, 400 rows 3,300ms), so raising the page size compounded it. After: **flat 207ms, nested 0ms, waterfall 0ms**, with 400 rows costing 2 built cards and 559 DOM nodes instead of 400 and 12,305. At 1,016 rows (infinite scroll accumulating pages) it is 14 cards / 1,540 nodes, nested still 0ms, flat 795ms. **Waterfall never needed this** and is the reference for why: it renders compact rows and builds a card only on expand, which is why it was always ~100ms where the other two were seconds. Things that must stay true when touching this: the `@placeholder` height must match a **collapsed** card (measured live at a uniform 144px regardless of content — mirrored in `.call-card-placeholder` in `styles.scss` *and* `COLLAPSED_CARD_HEIGHT_PX` in the component, **change one and you must change the other**), or the scrollbar lies and the page jumps as each card materialises; the nested view sizes its placeholder *per subtree* (`subtreePlaceholderPx`, one card-height per call in it) because one root may stand for a single call and the next for a dozen; and the flat list **opts out entirely while drag-reordering is enabled** (session-cycle custom ordering) because `cdkDropList` has to measure every `cdkDrag` item and an un-built card has nothing to measure. Selection is unaffected because it was never DOM-driven — verified live: "Select all" selected all **1,016** calls while only 323 cards existed. `@defer` never un-builds a card once built, so this bounds the *burst*, not the total; that is the deliberate trade for not having to re-virtualise rows whose height changes when expanded.

**Parent resolution is O(n²) but must not also re-parse timestamps.** `canOwn` used to call `windowOf` on both sides of every comparison, so a page of n calls parsed the same handful of timestamp strings ~2n² times; `indexCallTree` then ran the whole resolution **twice** (once via `buildCallTree` for the edges, again purely to collect `ambiguous`). Precomputing each call's window once (`CallWindow`/`indexWindows`) and resolving once (`resolveAllParents`, shared by `buildCallTree` and `indexCallTree`) is ~17x on that work with an identical set of comparisons and identical results — 400 calls 81ms → 5ms, 1000 calls 518ms → 30ms. Worth knowing: this was **not** what made the list slow at 400 rows (the card construction above was), so it is measurable but invisible there; it is what keeps the tree cheap into the thousands.

**Comments** are identified by `(callId, block, lineIndex)` against the *unfiltered* pretty-printed text, so "Lines only" filtering can never shift a comment onto the wrong line. `callId` here is always `call.id` (the backend-assigned UUID, see docs/architecture.md), never `callKey()` (the content-hash used for selection/pins/trackBy/dedup) - every call site that reads/writes/lists comments (`JsonPanelComponent`'s `callId` input as wired from `CallCardComponent`, `CallActionsComponent`/`BulkActionsBarComponent`'s comment fetches for export, `commentsByCallId` maps passed into the export builders) passes `call.id`. Mixing the two would silently split a call's comments across two different keys. They sync live across tabs via `BroadcastChannel` (incoming broadcasts never re-broadcast, or tabs would echo forever). Loading is lazy for free, not via any special-cased logic: `JsonPanelComponent.ensureLoaded()` already ran in its constructor, but a card's four `JsonPanelComponent`s are only ever constructed once `detailState() === 'loaded'` (see above) - gating the panels' existence behind that state was enough on its own to stop the previous eager "fetch comments for every visible call's every block on render" pattern, with zero changes to `CommentsStore` itself.

**Theming** is one `data-theme` attribute + one CSS variable block per theme (`ThemeService`, `localStorage['alfred-theme']`) — no component branches on theme. Custom popovers (`EmojiPickerComponent`, `SelectPickerComponent`) use `position: fixed` computed via `shared/utils/popover-position.ts`'s `computeFixedPanelPosition()`, which walks up for the nearest CSS-Transforms-spec containing-block ancestor (`backdrop-filter`/`transform`/etc.) rather than assuming the viewport — needed because `header`/`.tab-nav` set `backdrop-filter` for glass themes.

**No export path (`.md`/`.json`/`.html`/cURL) ever truncates or summarizes call data** — a hard correctness requirement; test coverage in `*-builder.spec.ts` asserts on large generated bodies specifically to guard this.

**Every readable export opens with an "About This Document" section, derived once in `shared/utils/export-narrative.ts` and rendered per format.** It states, in plain language, what the file is, whether it holds one call or many, which direction each call went (inbound = arriving at a service Alfred fronts; outbound = made to a third party), how many levels deep the capture nests, who called whom (as a monospace tree using the export's own call numbers), where the time went, any caveats (failures named individually, in-progress calls, ambiguous parentage), and — always, even when there are none — what a 🚩 comment is. Exports get handed to people and agents who weren't watching the traffic happen, and without this they receive a wall of JSON with no statement of which side of which service it came from. **Shared, not mirrored per consumer**, unlike the split algorithm below: the split must stay byte-identical across builders because it decides which *blocks* exist, whereas this is one section of prose whose entire purpose is saying the same thing everywhere. `markdown-builder.ts`/`html-builder.ts` render it; `bulk-json-builder.ts` emits the whole narrative object as the payload's first key, `about`, so a reprocessor gets `depth`/`shape`/`topology` as data and an LLM gets `about.description` as a self-contained paragraph. Deliberately **not** applied to the Discord/cURL/Postman exports — a chat blurb, a shell command and a runnable collection, all of which a page of narrative would swamp. Slots drop out when they'd say nothing, so a two-call flat capture doesn't get an empty topology tree. Two honest limits: derived times are rounded to 2dp because `Date.getTime()` (whole ms) minus a fractional duration otherwise leaks float noise into the `.json`; and a *single-call* export describes its surrounding context from `overlapCandidates` (hence the extra parameter on `buildExportMarkdown`/`buildExportHtml`), which carries timing and attribution but no method or URL — so it can say "inside a 22,383 ms inbound call to Odeysys" and truthfully not more, and it only finds a parent at all when one happens to fall in the range `BulkActionsBarComponent.fetchOverlapsFor` queried (that range is the call's own window, which a containing call by definition exceeds).

**Every `<details>` in an HTML export (`html-builder.ts`) renders closed, never `open`** — the per-call wrapper in a bulk export and all four Headers/Body blocks in both single and bulk export - so opening the file shows a scannable list first, not every call and every block already expanded. Markdown's per-call `<details open>` wrapper is unaffected (a different, additive design: Markdown's collapsible sections are for de-cluttering a long scroll, not the reader's first view of the doc), only HTML's is collapsed by default.

**Every clipboard copy goes through `shared/utils/clipboard.ts`'s `copyToClipboard()`**, not `navigator.clipboard.writeText` directly — that API requires a secure context, which a plain-HTTP LAN deployment isn't; it falls back to `document.execCommand('copy')`.

**Interception (`pages/interception/`)** is a fifth top-level tab, not a Settings panel: Settings holds things you configure once, while this is an operational surface you toggle repeatedly while testing and which, when on, is changing real traffic. `InterceptionStateService` is root-provided and injected by the SHELL (`MainLayoutComponent`), not just the page, because the **paused count drives a badge in the tab bar** - a rule holding somebody's connection open has to be visible from Live Calls too, not only from the screen that can release it. Its two WebSocket events (`interception-rules-changed`, `interception-paused-changed`) are filtered apart rather than treated as one "something changed": a busy breakpoint pushes several paused events a second, and refetching the rule list on each would be constant work for a list that did not change. `PausedCallsComponent` keeps the app's **one** timer - a 1s ticker that re-renders a countdown from data already in hand and makes no requests, so the no-polling rule is intact. See docs/interception.md.

**`phaseOf(type)`/`isTerminal(type)` on `InterceptionStateService` are computed from the
`actionTypes` signal (`GET /interception/action-types`), not a hardcoded frontend list.** Every
place that used to hardcode which `ActionType`s are terminal or which phase they belong to -
`alwaysShortCircuits`/`conflictHint` in `rule-editor.component.ts`, the import preview's terminal
flag, `interception-panel.component.ts`'s phase filter - calls these two methods instead, so a new
action type declared once on the backend (`ActionType.Phase`, `ActionType.isTerminal()`) needs no
matching frontend edit. `actionPhase`'s old hardcoded logic survives only as the fallback used
before `actionTypes` has loaded once.

**`AnswerPickerComponent` (`components/answer-picker/`)** is how `ANSWER_WITH_RECORDED_CALL`/
`REPLACE_WITH_RECORDED_RESPONSE`/`ANSWER_WITH_FILE` get their `StoredAnswer`, rendered by
`rule-action-card` for exactly those three action types. A direction toggle (Outbound/Inbound) plus
a search box reuses `CallsApiService.getCalls(source, …)` rather than a bespoke picker endpoint.
The box takes `host:`/`path:`/`method:`/`status:`/`body:` tokens (`shared/utils/answer-search.ts`);
the Method/Status/When chips edit the same text via `toggleToken`, so the box is the only filter
state. Only ONE substring reaches the server (`toServerSearch`: body, else free text, else path,
else host) - everything else is checked client-side on 200-call pages, auto-reading at most 5 pages
until 10 rows show, then `Load more` by offset. The rule's own host/path/methods/projects arrive as
`rule*` inputs and narrow the list by default ("Matches this rule" chip, removable). Clicking a row
lazily fetches `getDetail` for a preview; only the preview's button copies. Copying posts
`copyAnswerFromCall`; on a 409 (`SecretsDecisionRequired`) it shows the
keep/strip dialog listing `secretNames` and warns that kept secrets travel with exported rules,
then retries with the caller's choice. Once an answer exists it shows status/size/source and a
`secretsKept` badge. An "Upload file" mode swaps the call search for `<input type="file">` plus a
`StatusPickerComponent`, posted through `uploadAnswer()` as `FormData`. A call card's Export menu
also has "Use as answer in a new rule…": `RuleDraftService` (root, handed over once via `take()`)
carries a `CallRuleDraft` to the Interception page, which opens `RuleEditorComponent` with
`[draft]` - seeding the match from the call and one `ANSWER_WITH_RECORDED_CALL` whose picker gets
`preselect` and copies that call at once, through the same keep/strip prompt. See docs/interception.md's
"Stored answers" section for the backend side of the keep/strip decision and the no-total-cap
retention rule.

**Pick a call from anywhere (`CallPickerService`, root).** Any feature can ask the user to pick
one call (`mode: 'single'`) or several (`'multi'`) from ANY tab: `picker.start({requester, title,
mode, returnUrl, returnLabel, resume?, refuse?, refuseOrigin?})`, then read the picks back with
`hasResult(requester)` (reactive - use it in an `effect`) and `takeResult(requester)` (handed over
once). The user moves freely between tabs; `PickBarComponent` (mounted once in `main-layout`) lists
the picks with where each came from and has Cancel / Return. A pick is a `CallRef {source, callId,
cycleId}` (`core/models/call-ref.model.ts`) - `cycleId` matters because a captured call keeps the
live call's id, so the id alone cannot say which copy was picked. Load one in full with
`CallRefDetailService.hydrate(ref, summary)`. Rules worth knowing before adding a requester:
- **Pick buttons come free with `app-call-card`**: `PickCallButtonComponent` (`<app-pick-call
  [call]>`) sits in `CallActionsComponent` and in each waterfall row, and renders nothing unless
  something is picking. A new call list built from `app-call-card` needs nothing; one that is not
  drops in `<app-pick-call>`.
- **Which copy a card shows comes from `CALL_ORIGIN`** (`core/state/call-origin.token.ts`), provided
  by the session-cycle detail page (cycle id + label). Absent means the live log. Resend reads it
  too, so a resend from a cycle page targets the captured copy.
- **The requester is usually destroyed while the user is away**, so it passes its own state as
  `resume` (JSON-safe - the whole session lives in `sessionStorage` and survives a reload).
  `cancel()` still hands `resume` back with no picks, so cancelling never costs unsaved work. The
  rule editor parks its whole form this way (`EditorSnapshot`, reopened by `InterceptionComponent`
  via `[snapshot]`/`[pickedAnswer]`) and closes itself, since its modal would cover the tab bar.
- Current requesters: the answer picker ("Pick from anywhere…"), the resend dialog ("Pick another
  call…"; mounted in `main-layout` so it opens on every page), and a cycle's "Add calls from
  anywhere…" (multi, refuses the cycle's own calls via `refuseOrigin`, copies with
  `copyCallsInto` on Return), and the multi-call resend editor's "Add calls from anywhere…".

**Finding a call, and copying one into a rule.**
- `CallFinderComponent` (`components/call-finder/`) is the one call search: `host:`/`path:`/
  `method:`/`status:`/`body:` tokens, chips, "Matches this rule", preview of the request or
  response (`[part]`), Load more, optional "Pick from anywhere…". It only emits `(chosen)` - the
  stored-answer picker copies an answer, "Copy from a call…" copies fields, the replace preview
  runs a find & replace. Use it rather than another search list.
- `CopyFromCallComponent` + `shared/utils/copy-from-call.ts` on SET_REQUEST_BODY,
  SET_RESPONSE_BODY, MOCK_RESPONSE and REPLACE_RESPONSE: tick body / content type / status /
  each header (secret ones tagged and unticked; Host, Content-Length and other per-call headers
  never offered) / method / URL. What the action can hold lands on it (a mock keeps its own
  headers map); the rest becomes ordinary actions right after it (`applyCopy`: one Set header per
  header, Set method, Rewrite URL) so every copied part is visible and editable in the lane.
  "Pick from anywhere…" parks the editor with `EditorSnapshot.purpose = 'copy'` and reopens the
  panel at "choose what to copy" with `[pickedCopy]`.
- `ReplacePreviewComponent` ("Try on a call…") on REPLACE_IN_*_BODY runs
  `shared/utils/replace-preview.ts` - the proxy's `_Pattern.replace` semantics (literal unless
  regex, case-sensitive unless off, at most N, Python `\1` templates) - against a picked call and
  shows the result in the embedded interception diff. Browser regex, so exotic patterns can differ.
- `MatchFromCallComponent` + `shared/utils/match-from-call.ts` ("Fill from a call…" on the Match
  section): direction, project (inbound), host (exact or `*.parent`), path (whole, a prefix, or a
  regex with ids generalised), method, plus headers / query / cookies as "Only when…" tests - all
  editable before they land, tests unchecked by default and "equals" their value - secrets and
  cookies too, tagged "secret" since a checked one saves its value in the rule in plain text. Checked fields replace the form's; tests merge by kind + name. The editor keeps the
  picked call (`matchFilled`) for Undo and a live `whyNotMatching` check that mirrors the proxy's
  `Match` (path tested with its query, `*.` hosts, header names case-insensitive). Pick from
  anywhere parks with `EditorSnapshot.purpose = 'match'`.
- Every rule-action body field uses `app-body-editor` (colours, find & replace, Format, big tab via
  `EditTabService`); the Interception page is lazy-loaded to keep this out of the initial bundle.

**Resend: one draft model, two dialogs, one journey panel.**
- `shared/utils/resend-draft.ts` is the only place a form becomes `ResendEdits`: `draftFrom(call,
  cycleId)`, `editsOf(draft)` (only what differs; a removed header → null, an added one → value;
  the body compared with `bodiesDiffer`, so **Format alone is never an edit** - a signed SOAP
  envelope goes out byte-for-byte unless its content changed), plus the "edit all at once" ops
  (`setHeaderOnAll` case-insensitive, `removeHeaderFromAll`, `findReplaceAll`/`countMatches`,
  `setMethodOnAll`, `setHostOnAll` - outbound only, inbound always goes to its project's listener -
  `setCurrentSessionOnAll`, `moveDraft`).
- `ResendCallEditorComponent` edits one draft with `app-header-editor` (Rows | JSON) and
  `app-body-editor` - the paused-call inspector's editor, same tokenizers and colours as the call
  card, with find and find & replace - and can open either part in a big tab (`/edit`, see
  `EditTabService`), whose edits stream back live over a BroadcastChannel.
- `ResendDialogComponent` (one call) and `BulkResendDialogComponent` ("Resend selected…": send
  order with drag/arrows/untick-to-skip, per-call editing, edit-all tools, stop-at-first-failure,
  delay between sends) both use it; both are mounted once in `main-layout`. The multi-call state
  and send loop live in `BulkResendDialogService` (root) so they survive the dialog hiding while
  picking more calls, and sends run strictly one at a time in list order, each tagged with a
  `batch {id, index, total}`.
- `ResendPanelComponent` on every resent call's card shows its whole cycle (original → edits →
  session → sent → rules → upstream → response) and embeds `InterceptionPanelComponent`
  (`[embedded]`, `[labels]`) for Original / Resent / Diff of the request AND the response. It finds
  the original through `resend_edits.origin {direction, cycleId}` (see `shared/utils/resend-summary.ts`;
  older resends without it fall back to the live log) and fetches nothing until opened.

**`ResendDialogComponent` (`components/resend-dialog/`)**, opened through a `ResendDialogService`
following the existing `ExportDialogService` pattern, edits a hydrated call's method/URL/headers/
body and posts it through `resend-api.service.ts`'s `resend(req)`. The "Resend with current
session" checkbox asks the backend to substitute the newest cookie/authorization value for the
call's host (`FindRecentRequestHeadersUseCase`, see docs/architecture.md) rather than sending the
original's stale ones. The result view is a link to the new call plus which session values were
substituted - **names and source call ids only, never the values themselves**, the same
never-leak-a-secret rule every other interception surface follows. `call-actions` adds a "Resend…"
entry and `bulk-actions-bar` a bulk "Resend selected" that sends one at a time in the selection's
display order with a progress count, stopping on the first 409; a resent call's card gets a "↻
resend of `<id>`" chip linking back to the original, edits summarised in its tooltip.

**`WsMessagesComponent` (`components/ws-messages/`)** renders one call's WebSocket message list -
a windowed list with a direction arrow, timestamp and type per message, an edited/dropped badge
with the original content viewable, and "N earlier messages not recorded" when the backend's
per-call cap (`call_ws_message`, see docs/architecture.md) has dropped any. `call-card` shows
"WebSocket · N messages" for a status-101 call and embeds it only on expand, fetched via
`getWsMessages(source, id, offset, limit)`; `calls-state.service.ts` re-fetches an open panel on
the `ws-messages-appended` WebSocket event, following the same no-polling, fetch-on-demand shape as
everything else in this file. Exports carry WebSocket messages the same never-truncate way as
everything else: `bulk-json-builder.ts` adds `wsMessages` to a call's event and `import-parser.ts`
reads it back as the exact inverse, `markdown-builder.ts`/`html-builder.ts` render every message
untruncated.

**Four top-level routes/tabs** (`app.routes.ts`, nav in `layout/main-layout/`): Live Calls (`''`), Session Cycles (`cycles`, `cycles/:id`), Profiles (`profiles`), Settings (`settings`). There's no separate "Internal Calls" tab — inbound (frontend→WildFly) traffic is a **source filter inside the existing Live Calls dashboard** instead: `CallSource = 'external' | 'internal' | 'both'` (`core/models/call.model.ts`), switched via a picker in `HeaderComponent` (dashboard-only). `CallsStateService.setCallSource()` swaps which backend endpoint pair (`/calls` vs `/internal-calls`, REST + WebSocket) feeds the same `CallCardComponent`/`CallListComponent` — no forked UI for the second traffic direction, just a different data source behind the shared components (see docs/architecture.md for `backend-internal-calls`).

**Settings (`pages/settings/`)** has three partitions, tab-switched by a local signal — three genuinely different concerns sharing one page, not one feature:
- **Call filtering** (default) — accept-all/accept-only mode plus a host whitelist/blacklist (`CallFilterSettingsStateService` → backend's `backend-settings` slice). Controls which *outbound* supplier calls get logged in the first place, upstream of everything else in this doc.
- **Database** — read-only storage stats (per-store row counts/sizes) plus destructive "Clear all calls"/"Clear all cycles" actions, gated behind `ConfirmDialogService`.
- **Inbound logging** — only rendered if `InternalLoggingApiService`'s `getFeatureEnabled()` (the deploy-time `reverse_proxy_enabled` flag, `GET /internal-calls/feature-enabled`, fetched once) resolves true; many deployments only need outbound logging and hide this panel entirely. When enabled, lists every project from `settings.properties`'s `internal_call_services` (plus a reserved `unknown` row), showing each one's `localhost:<listenPort> → <upstreamPort>` mapping with its own Enable/Disable button via `getServices()`/`setEnabled(name, enabled)` (`GET /internal-calls/services`, `POST /internal-calls/services/{name}/logging-enabled`) — mirroring `toggle-wildfly-reverse-proxy.sh`/`.bat <name>`. Flipping one project never affects any other, or whether calls still reach its upstream, only whether that project's calls are recorded (see docs/supplier-integrations.md).

**`pages/json-view/`** is a fifth route (`/view`, deliberately outside the tab layout, opened via `window.open`) that reopens `JsonPanelComponent` full-page for one stored call block — a "pop out this JSON" affordance, not a new feature surface.

**With both sources selected, each backend is paginated on its OWN cursor** (`CallsStateService.mergedCursor`), not on the caller's `offset` — that counts calls loaded across both stores and means nothing to either one alone. The shared offset was a real data-loss bug: with 178 external and 200 internal calls, page one merged 378 and trimmed to the 200-call limit, then page two asked *both* backends for offset 200, where each had already run out. The 178 trimmed calls were unreachable, the list stopped at 140 visible rows, and every further "load more" fetched an empty page forever. Nothing is trimmed now, so a merged page can be up to twice `limit`; a call dropped from a page can never be asked for again, because the only handle on it is an offset into a source that has moved past it. Cross-page ordering stays approximate — page two's calls all sort after page one's even if one source ran out early — which is a far smaller problem than missing calls.

**Each level of nesting has its own hue** — `depthTintClass` returns `depth-tint-0..3` (cycling every four), and those classes set a `--depth-color` custom property that the waterfall rail, the nested view's children rail, and a sandwich card's two bands all read. It exists because `depthRailPx` caps indenting at `MAX_INDENT_LEVELS`, so past that point two different depths were drawn at the same x and a chain of callers could only be counted by eye. **Green, amber and red are deliberately not in the ramp**: they mean status and duration everywhere else in Alfred, so a level-2 rail in green would read as a health signal. In the nested view the tint rides on the `app-call-tree-node` host, so a card inherits its level without being told its depth and a nested node re-sets it for its own subtree; the *rail* takes `depth + 1`, since it introduces the level below rather than describing the card it hangs off. **A waterfall row draws one guide line per ancestor level plus its own** (`depthRails`), ancestors at 26% and its own at 90%, because a single line at the row's own indent says how far in a call sits but nothing about what it sits inside — a depth-2 row was one short tick floating in space, with nothing beside it for its hue to be read against. The lines are added *inside* the indent `depthRailPx` already reserved, so nothing moves; past `MAX_INDENT_LEVELS` the ancestors run out of room but the last line still carries the row's own level, or depth 4 would be drawn as depth 3. The nested view needs none of this — its ancestors are literally the cards around it. The tint lands on the bands' background rather than the card's border because `.call`'s border-color and box-shadow are already spoken for by selected/pinned/error/warning states.

**In the two tree views, selecting a call selects everything nested under it, and the checkbox is tri-state.** `CallSelectionState.setSubtreeSelected`/`subtreeSelection` are the whole surface; `call-tree.ts`'s `indexDescendants` supplies the subtree, and `subtreeSelectionOf` in `call-utils.ts` is shared by both concrete states so a half-filled box can't mean two different things on the dashboard and in a session cycle. The flat view deliberately keeps plain `toggleSelected` — it draws no hierarchy, so a half-filled box there would refer to nothing on screen. A parent stays selected in its own right after a child is unticked (it's still a call, and still exports); 'some' is what makes that visible instead of the box overclaiming. Clicking a half-filled parent *fills* it. Drag-paint latches subtree mode at `startDragSelect` rather than asking each card, so one drag can't be half one rule and half the other. **The reason any of this needed writing is that the nested view was already selecting — upwards.** `mousedown` bubbles, and nested cards are literally inside one another, so every ancestor card ran `CallCardComponent`'s host listener too: measured on a real trace, pressing one supplier call at depth 2 selected three calls, itself plus its parent plus its grandparent. The fix is one `stopPropagation`, and it is load-bearing — without it the subtree rules above are applied to the wrong calls.

**Folding is per-call-id, shared by both tree views, and deliberately not persisted.** `CallListView.foldedIds`/`setFolded`/`foldAll`/`unfoldAll` — nothing to do with the neighbouring `expanded`/`collapseAllVersion`, which are about a card's own Headers/Body panels; this hides a parent's *children*, not its payload. Folding a parent takes every foldable call under it along, so reopening returns one level instead of however many were open before — on a deep trace, restoring the whole subtree in one click undoes the entire point of having folded it. Unfolding touches only the one call. Folding never changes selection, and a folded parent still reads half-filled if something inside it is ticked, so hidden calls can't silently ride along into an export unnoticed. Only calls with children are ever put in the set (`foldableIds`), since folding a leaf is a no-op that `unfoldAll` would then have to clean up. The waterfall keeps a folded group's opening/closing bracket — it carries the timing — and drops only what sat between the halves: on a live 14-call trace, fold-all took 18 rows to 5. It is not persisted because the set describes one particular page of loaded calls; restoring it against a different page would fold calls the user never folded.

**"Only calls with nested calls" keeps a parent AND everything under it, so a kept chain is never rendered hollow.** `CallListView.nestedOnly`/`setNestedOnly` narrow the list to the calls that take part in a nesting relationship at all — `call-tree.ts`'s `nestedCallIds` keeps a call that has children *or* sits under one that does, so the only thing dropped is a call that caused nothing and was caused by nothing. Keeping parents while dropping their descendants would have been the literal reading of "calls with children" and is the wrong one: in the nested view it renders a parent card that visibly contains nothing. Because the rule is per-call rather than per-subtree it means the same thing in all three views — the flat view loses exactly the cards the nested view loses whole. It is **client-side and never refetches**: "has children" isn't a property the backend could index, it's derived by comparing every loaded call's window against every other (`buildCallTree`), so it can only be answered over the calls in hand — which also means a parent whose children haven't loaded yet reads as childless until they do. It sits *after* the pin/status narrowing and *before* the sort, so the tree is built over exactly the calls the list would otherwise show (building it earlier would find parents among filtered-out calls, and keep children whose parent isn't there), and `stats()`/`supplierOptions()` stay scoped further up so turning it on never shrinks the stat pills it's read against. Unlike `showOptionsCalls` it is **not persisted** and it **does** earn a removable chip in the header: it can hide most of a list, and a preference that survived a reload would silently explain an almost-empty page on a later visit. Verified on a real 62-root session cycle: 56 standalone roots dropped, the 6 genuine chains kept intact at 16 calls — identical to the count of chained calls measured before filtering. Both the dashboard and a session-cycle detail page get it from the shared `createCallListView`, so neither had to be touched.

**An internal call is bracketed into a `request` half and a `response` half exactly when the call tree gives it children — one rule, everywhere.** The flat list gets there via `call-utils.ts`'s `computeSplitCallIds`, each export format via its own line-for-line mirror of it (`html-builder.ts`/`markdown-builder.ts`/`bulk-json-builder.ts`, per this codebase's mirror-per-consumer convention), and the nested/waterfall views via `call-tree.ts`'s `buildCallTree`; all four ask the same two questions of a candidate — is it strictly contained in the call's window, and is it attributable to that call (`passesOwnershipCheck`) — and hand a candidate contained by several calls to the innermost of them, vetoing only owners that merely *overlap*. There used to be a third question: a call whose surviving set was a single child had to clear a "blocking signature" (that child covering ≥30% of the parent and ending within its tail window) before the nesting counted. It was meant to reject coincidental containment, and it instead **silently desynchronised the exports from the waterfall** — a 24.84s odeysys call with one 2.86s core-service call inside it (11.5% coverage) came out of every export as a single unbracketed block, with its four supplier calls dumped after it instead of inside it, while the waterfall bracketed it correctly. The 11.5% was the *finding* about that call — odeysys spent 80% of itself before issuing a request — not grounds for flattening its structure. Keep the four implementations answering identically; when they diverge, an export stops matching the screen it was taken from, which is the one thing an export cannot do.

**An exported .html builds a block only when that block is opened, and renders a big one through a render window.** Every Headers/Body block in the export is a `<details>` that starts **closed**, yet the document's embedded script used to call `initJsonBlock` on all of them at load, materialising three elements per line plus one `<span>` per token for content nobody could see. Measured on a real 6.6MB 8-call export (one call's response body pretty-printed to **110,152 lines**): **1,300,952 DOM elements** and 170,608 rendered lines before the first paint, 2.0s to open, 4.5s to scroll, and **5.6s per keystroke** in a block's find box, because each keystroke re-rendered the whole block synchronously. After: **482 elements at load, 284ms to open, 807 elements after opening the 110k-line body, 12ms to scroll, 163ms to search.** Three changes, in order of effect: (1) a block is built on its `toggle` event, and a block that ships `open` waits for an `IntersectionObserver` instead of building up front; (2) past `VIRTUAL_MIN_LINES` (400) a block becomes its own bounded scroller and renders only the visible rows plus overscan, positioned with `padding-top`/`padding-bottom` so normal flow - and therefore the existing horizontal scrolling of `white-space: pre` lines - keeps working; (3) a chunk is built as ONE HTML string rather than `createElement` per line and per token. The window arithmetic is exact rather than estimated because `.json-line-content` is `white-space: pre` inside an `overflow-x: auto` container, so **no line ever wraps and every row is one uniform height** - measured from a real rendered row rather than derived from the stylesheet, since browsers round `font-size x line-height` differently. A flagged line is the only variable-height case (it also renders a comment card), so those heights are measured after paint and folded back into the offsets; verified live, the scrollbar on a 110,152-line body lands within **32px of 2,313,192px**, and scrolling to the bottom shows line 110,152. **Below 400 lines nothing changes** - the block renders in full, in normal flow, exactly as before. Two invariants that must survive any future edit here: the find box counts matches by scanning the raw `lines` array, never the DOM, so "1/521" is exact across the whole body while only ~40 rows exist; and **Copy always copies every line**, never the window - an export never truncates. The summary now states each block's line count, since you can no longer discover it by opening the block cheaply.

**The readable exports show nesting twice: the Calls list is indented to match the topology, and a waterfall says whether children ran in parallel or one after another.** The About section's tree already said who called whom, but the `## Calls` list below it rendered every block flat, so the structure was only implied by ordering (a split parent's request and response bracket everything it caused). Both `.md` and `.html` now indent each call block by its `depthByCallId` depth, and the two halves of a split parent sit at the same level with its children between them. The mechanisms differ because the media do: HTML gets a real `margin-left` plus a `::before` rail, while Markdown uses `&nbsp;` runs and a `└─`, since GitHub and most other renderers strip inline CSS from a `<details>` but keep both of those.

The waterfall answers what neither the tree nor the duration column can: two siblings of 3,038ms and 4,101ms are indistinguishable from two that ran together, yet on a real capture they sum to *exactly* their parent's 7,212ms of downstream time - strictly sequential, and roughly 3s of avoidable latency. **It is drawn as one band per parent, each scaled to that parent's own window, not as one chart on a shared axis.** The shared axis was the obvious design and it does not survive real data: measured on an actual export, the root runs 248,852ms while the interesting children live in a 7,212ms window inside it, so every child collapsed to the same single indistinguishable character and the chart conveyed strictly *less* than the numbers beside it. Per-parent bands cost one caption line each and make the sequencing plain. Each band states its own span, so no bar can be read against the wrong scale. `NarrativeCallNode.startOffsetMs` exists for this - without a start time a topology is only a list of durations - and it is in the `.json` too, so an agent can reconstruct the same chart. A flat capture produces no bands at all rather than a column of identical full-width bars. Each band is drawn as a Gantt chart: the parent's own span as a dashed outline track, its children as solid bars positioned inside it, 25% gridlines, and a time axis labelled from the band's own span (`waterfallAxisTicks`, unit-switching so a 4-minute call reads `4m0s` rather than six figures of milliseconds). Children are coloured by direction - inbound into one of our services, outbound to a third party - and red when failed or in progress. Without the axis the chart is only a picture of relative widths: it can say "this one is wider", not "this started four seconds in". **The parent's own row is split into own-work / waiting / own-work**, so you can see *where* on the parent its children ran - a parent that fans out immediately reads completely differently from one that fans out at the very end, and a plain full-width bar said neither. Own work is drawn solid and waiting hollow, not the other way round: the parent's own time is the part you can do something about, and a row that is almost entirely hollow says at a glance that the call did nothing but wait. The waiting span is the ENVELOPE of the children (first start to last end), not the sum of their bars - between two sequential children the parent is still waiting, not working. On a real capture this is the whole finding: one 211,751ms call renders almost entirely solid, because only 6,884ms of it was downstream. **Charts are linked to each other rather than left as islands**: a nested chart is indented, joined by a rail to the row it expands, and captioned "inside call N" with an anchor link, while the row it expands links down to it. The same call otherwise appears as a row in one chart and as the parent of the next, and nothing says they are the same call - which matters most exactly where the tree is widest, when a parent has several children that are themselves parents. Watch the recursion's entry point: `topology.flatMap(bandsOf)` passes flatMap's *index* as the second argument, so every root claimed to sit inside call 0 until it was wrapped in an arrow function. **The exported document is themed slate**, matching `[data-theme="slate"]` value for value, with that theme's translucent surfaces pre-flattened to solids since an export has no theme layer to composite against.

**An exported document is self-contained, so its CSS may only use custom properties it defines itself** - guarded by a test, after the waterfall bar shipped as `var(--purple)` when this file's palette only defines `--purple-light`. The app defines both, so it read correctly in review; in the export the property resolved to nothing and every bar rendered fully transparent. A missing colour is invisible rather than broken, which is the kind of thing review stops catching.

**Redaction is manual, and a redaction record stores the NAME of a secret, never the secret.** Exports carry real `authorization` headers, `set-cookie`, `x-api-key` and tokens in bodies (measured across 40 real calls: authorization in 35, set-cookie in 35, x-api-key in 5, plus `access_token`/`bookingToken`/`bookingSignature` in bodies and `credential=` in query strings). The user marks what to hide by clicking a line, the same gesture as flagging an issue - nothing is ever pattern-matched or hidden automatically. Three decisions are load-bearing.

*Why a name and not a line.* The obvious implementation - store redactions as comments, since a comment is already "an annotation pinned to a line" - leaks the secret. `html-builder.ts` and `markdown-builder.ts` echo a comment's stored `lineText` verbatim into the Flagged Issues section, so a redaction holding the raw line would reprint the token in full, directly below the masked copy, in the very file the user redacted in order to share safely. Storing only the header name / body key / param name also keeps secrets out of the redactions store's own backups. `redaction.model.ts` says so at the field, because this is the kind of constraint someone later "helpfully" relaxes.

*Why the value is masked and not the line blanked.* Bodies are pretty-printed JSON. Blanking a line leaves `[REDACTED]` between two commas, which is no longer valid JSON - it breaks the `.json` re-import and every downstream consumer. `"authorization": "***REDACTED***"` keeps the document well-formed and preserves the diagnostically useful fact that auth *was* sent.

*Why one choke point.* `redactCalls()` is applied once in `export-dialog.component.ts`'s `buildContent`, which is the single place any of markdown/HTML/JSON/Postman gets its calls, plus the two standalone paths in `call-actions` (copy-as-cURL and the single-call JSON download). Masking inside the builders instead would be six implementations and six chances to forget one, and the cost of forgetting is not a cosmetic bug - it is shipping a bearer token to whoever received the file. A format added later is redacted without its author knowing redaction exists. The guard test asserts that none of six planted secrets survives anywhere in the serialised output.

Body keys match by name at any depth including inside arrays, since a token nested three objects deep is the same token; a body with no match is returned byte-identical rather than re-serialized, so a 5.9MB payload is neither reformatted nor parsed for nothing. A URL redaction rewrites both `url` and `original_url` - masking only the first leaves the secret one line up in the .md/.html output. The value stays fully readable in Alfred itself: you need the token to debug, and it is the shared file that leaks, so the UI marks the line rather than hiding anything on screen. `RedactionsStore` loads eagerly at startup, unlike `CommentsStore`'s lazy per-call cache, because an export can fire from a card menu with no panel ever opened and a not-yet-loaded list would redact nothing while reporting success. The `.json` carries `redactedValueCount`, and the import dialog leads with it - re-importing a redacted export is lossy in a way nothing else about the file reveals, since the calls land looking complete with `***REDACTED***` where a token was. Wire values are kebab-case (`call`, `request-header`) to match `Comment.block`'s existing convention; `RedactionsControllerTest` pins that, because a mismatch there means every hide 400s and the user finds out only after sharing the file.

**A big .md export is a different problem with no code fix.** The same capture is 6.05MB and 171,082 lines of Markdown, ~5.9MB of which is that one pretty-printed response body inside a single fenced block. Markdown has no lazy rendering, so whether it opens is entirely down to the viewer: most previewers (GitHub above ~1MB, and any highlighter that tokenises a fence in one pass) give up on a 110k-line code fence. Leaving the body unformatted would trade 110k short lines for one 5.9MB line, which is worse in most editors, and truncating is forbidden (see the no-truncation rule). For captures with very large bodies the .html export is now the format that actually opens; .json remains the machine-readable one.

**The ambiguity veto asks about WINDOWS, not attribution - and `call-tree.ts` drifted from that for a while, silently orphaning real parents.** When several calls contain a candidate, the innermost takes it *provided the owners form a nested chain*; only owners that merely OVERLAP, neither inside the other, are genuinely ambiguous. `computeSplitCallIds` has always tested that chain with `strictlyContainsCall` - pure time containment. `call-tree.ts`'s `resolveParent` tested it with `canOwn`, which additionally refuses an internal call owning another internal call of the SAME service. Those are two different questions: the same-service rule exists so a service isn't credited with calling itself, but "is owner A inside owner B" is about position alone, and two `odeysys` calls one literally inside the other *are* a chain. Conflating them meant a second, outer same-service owner made the owner set look unchained, the veto fired, and a call with a perfectly good parent was thrown to the root and flagged ambiguous. Found on a live session cycle: a **193-second** `GET /Master2/airline/?status=1` (odeysys) spans most of the capture, so the supplier call made by a 5.9s `POST get-upselling-flights` (also odeysys) had two owners; `canOwn(long, short)` is false purely because they share a service, so the supplier call was orphaned. Measured over that cycle's 43 calls: **40 roots / 3 nested / 2 ambiguous before, 38 / 5 / 0 after** - every external call correctly attributed, and the rendered tree matches those numbers exactly. **Why it looked like a session-cycles-only bug:** cycles disable server-side pagination and load the entire capture, so a long-running call is always present to trigger it, while a 10/25/50-row dashboard page usually doesn't contain one - the dashboard was equally affected whenever such a call happened to be loaded. The fix is `strictlyContainsWindow`, the `CallWindow` counterpart of `strictlyContainsCall`; the ownership rule itself is unchanged, so same-service calls remain siblings and genuinely overlapping owners are still vetoed.

**`index.html` is served `Cache-Control: no-cache`, and the hashed bundles `immutable` - without that, a frontend fix silently never reaches anyone.** `frontend/nginx.conf` used to send no `Cache-Control` at all, only `Last-Modified`/`ETag`. A browser given no directive falls back to **heuristic caching** (roughly 10% of the age since `Last-Modified`) and serves the file without revalidating - and `index.html` is the only file that names the content-hashed bundle, so a stale copy pins the browser to the PREVIOUS `main-<HASH>.js` indefinitely. The whole app keeps running old code while the container serves new code, and a rebuild appears to change nothing. Confirmed live twice in one session: the container served `main-AWMJIZKU.js` while the open page ran `main-4ZEWT52Q.js`, and a genuine, tested bug fix read as "still broken" until a hard reload. The conditional request this adds is answered `304` from the `ETag` that was already being sent, so it costs one round trip per load and nothing else; everything with a content hash in its name (`.js`/`.css`/fonts/images) is cached a year and `immutable`, since a new build produces a new filename. `/env.js` is written at container start rather than build time, so it gets `no-cache` too, via an exact-match `location` (nginx ranks `location =` above a regex `location`, so it wins regardless of order). The SPA fallback (`try_files ... /index.html`) does an internal redirect that re-runs location matching, so deep links like `/cycles/<id>` pick up the `no-cache` header as well - verified with `curl -I` on `/`, `/env.js`, `/main-<HASH>.js` and `/cycles/abc`.

**The .json export is the re-import format, and it must round-trip losslessly — `import-parser.ts` is the exact inverse of `bulk-json-builder.ts`.** Re-importing an export used to be impossible: the exporter writes `{ about, metadata, exportedAt, summary, **events** }` keyed by `callId`, and the importer read `parsed.calls` keyed by `id`, so **zero of 44 events** in a real 30-call export were readable. Four separate defects stacked: the key name, the id field, no `groupBy(callId)` (a resolved internal call is TWO events — the response half carries no url/method, so any per-object reader drops it and the call comes back with no status, duration or response body), and `source` never being copied — which mattered most, because `copyCallsInto` does `call.source ?? 'external'` and so filed every inbound call into the outbound store, and only `source === 'internal'` may own children (`call-tree.ts`'s `canOwn`), flattening every chain in the file. **The reason this shipped broken is the thing to keep fixed:** the importer's tests asserted against hand-written `{ calls: [...] }` fixtures of a shape `buildBulkExportPayload` has never emitted, so they passed while the feature could not read one real file. Fixtures for import **must** come from `buildBulkExportPayload` — `import-parser.spec.ts` and the dialog spec both build their input by exporting real `CallRecord`s and serializing. The export now also states `source` and `state` on its events rather than leaving them to be inferred: a non-null `service_name` usually means inbound, but an **outbound** call carries one too once its project opts into forward-proxy outbound attribution (see `CallRecord.service_name`), so inferring silently misfiles exactly those deployments. Files exported before `source` existed still import — `inferSource` guesses from `service_name` and the dialog shows an amber `parseWarning` naming how many calls were guessed, rather than importing quietly. Merging is field-by-field and never overwrites an already-set field, and a split call is dated at the **earlier** of its two events, since the response event's timestamp is start+duration and events are file-ordered by their own timestamps — dating the call at its end would destroy the containment that nests its children. Verified end-to-end on a real 4.7MB 30-call export: 13 roots with subtree sizes `[4,3,3,2,2,2,2,2,2,2,2,2,2]` in the file's own `about.topology`, and **identical** after export → import → render, both via the inference path and via a fresh export with `source`.

**`about.readingGuide.topology` points a consumer at the call graph instead of at `events`, because iterating `events` is the trap.** The .json export is two documents in one: `about` exists to be *read* (in practice by an AI agent handed the file), `events` exists to be *parsed back* by the importer. Those pull in opposite directions, and the naive read of `events` is wrong in a specific way — there are more events than calls, since a split inbound call emits a `request` event carrying url/method and a `response` event carrying status/duration and **no url or method at all**. A consumer that treats one event as one call therefore sees two half-calls per split call, one of them urlless. That is not hypothetical: it is exactly the mistake Alfred's own importer shipped with. So `readingGuide` now leads with `topology`, naming `about.topology` as the self-contained answer to who-called-whom and where-time-went (one node per call, already merged and nested, with `downstreamMs`/`selfMs` per node), and `readingGuide.events` states the two-events-one-callId hazard outright and points at `about.counts.calls`/`about.topology` as authoritative for the call count. Measured on a live 22-call export: `about.counts.calls` 22 vs `events.length` 26 — the discrepancy the guide exists to explain. **The guide is .json-only** — the .md/.html builders render the prose fields and have no `events` array to warn about. **Changing it cannot affect re-import**: `parseImportedCalls` reads only `events`/`calls`, never `about`, and `import-parser.spec.ts` pins that with a test that imports a payload with the entire narrative stripped out and one that reimports after rewording the guide, both asserting a byte-identical result. Re-verified live after the wording change: export 22 calls → re-import → 18 internal + 4 external stored, rendering 16 roots over 22 calls, matching the file's own `about.topology.length` and `about.counts.calls` exactly.

**Call diagnostics (`shared/utils/call-diagnostics.ts` + `components/call-diagnostics/`)** answer "where did this call's time actually go", which a waterfall cannot: a waterfall shows how long each call took, but the time *between* calls is whitespace, and on real traffic the whitespace is most of the request. `analyzeCall` assigns every millisecond of a root to exactly one bucket — `duration = setup + upstream + between + tail`. **`upstream` is the UNION of the children's windows, not their sum**: calls running in parallel occupy one stretch of wall clock, and summing them would claim more time than the request took. That union is also what makes "time between calls" well-defined when calls overlap — rather than n² per-pair gaps that can go negative, `between` is time inside the fan-out window with nothing in flight, which degenerates to the obvious gap when calls are sequential. Direct children only: a grandchild happened inside a child, so it belongs to that child's accounting, and mixing depths would double-count — which is also why **every call with children gets its own panel, at any depth**, rather than only the root. `analyzeCall` was always depth-agnostic; the waterfall's row builder was gating it on `depth === 0`, which hid the breakdown for the call you usually want it for — the service in the middle that actually did the fanning out. On a live trace the root reads "74% of this call runs before the first request goes out" while the `core-service` call inside it reads "76% of this call is spent waiting upstream": two different diagnoses of two different calls, and only the second one points at the suppliers. **Nothing renders one until a `diagnose` button is pressed**, and the panel then opens *attached* to the call it describes: in the waterfall, directly above that call's own row with a shared edge (`.waterfall-diag` zeroes `.diag`'s top margin and `.waterfall-row-diag` drops the row's top border, so the two read as one block); in the nested view, as the first child of the card itself, above the request band. With several calls in a trace able to show a breakdown, a gap would leave it ambiguous which row a panel belongs to. The nested view gets the panel by **projection** (`[callDiagnostics]`) rather than building it in `CallCardComponent`: only `CallTreeNodeComponent` holds a `CallTreeNode`, and gating the projection on the open state means a page of parents costs no `analyzeCall` until one is actually asked. The button sits at the far right of a waterfall row (where the old always-on `▼ diagnose` label was) but with the other per-call actions on a nested card — that band's right edge is the request/response marker and the timestamp after it already wraps to its own line, so a button out there reads as belonging to the date. Per call it derives **slack** (how much slower this call could get before the total moves) and hence the critical path — on a measured live trace only 1 of 5 calls had zero slack, so optimising the other four would have changed nothing. The findings engine reports the dominant phase, sequential fan-out (what an `await` in a loop looks like: nothing overlaps and the total jumps without any one call slowing down), failures, and healthy parallelism. **Duplicate detection never claims two requests are identical from method and url alone** — `analyzeCall` only returns *candidates* (same method, same full url, within 150ms) and `CallDiagnosticsComponent.confirmDuplicates` fetches both request bodies and compares them before saying anything. That distinction is not academic: on real traffic two calls to one `FlightSearch` endpoint 27ms apart carried `{"supplier":"Galileo"}` and `{"supplier":"TravelportNdc"}` — a legitimate two-supplier fan-out that the url-only rule called duplicated work. Bodies aren't in the list payload, hence the fetch; it happens only on expand and only for calls that already match, and if a fetch fails nothing is claimed. Headers are deliberately excluded from the comparison — they routinely carry a per-request id or a freshly signed token, so genuinely duplicated calls would differ there and the check would never fire.

**Per-call network phases come from the proxy** (`proxy/log_and_route.py`'s `_phase_timing` → nullable columns on `call_metadata` → `CallSummary.timing`), and answer *why* a call was slow rather than just that it was. Two non-obvious properties: **connect and TLS happen INSIDE the time-to-first-byte window**, not before it, because mitmproxy opens the upstream connection lazily — rendered as four consecutive segments they summed to 328ms for a call that took 196.62ms, so `CallDiagnosticsComponent.phases` subtracts the handshake out of `ttfb` to leave the upstream's own think time. And mitmproxy **reuses** connections, so `connect_ms`/`tls_ms` are only reported when the handshake actually happened during that request — their *presence* is the finding, since paying for a handshake on every call means connections aren't being pooled. Null anywhere means NOT MEASURED, never zero; a call logged before this existed must not read as "measured, and instant". `CallTiming.isEmpty` needs `@JsonIgnore` — Jackson treats any `isX()` on a record as a property and was serializing an extra `"empty": false` onto every call in every list response. **Session cycles have to persist these too, and didn't:** `captured_call_metadata` had no timing columns and `completeCapturedCall` took no `CallTiming`, so a cycle's diagnostics panel rendered no per-call phase bars while the identical panel on the live list did — same component, one side simply had nothing to draw. The timings only exist at *completion* (the captured row is written while the call is still in flight), so they have to be threaded through `SessionCycleCaptureAdapter.onCallCompleted` → `CapturedCallsStorePort.completeCapturedCall` → the UPDATE, on top of the `append`-time bind for an already-resolved call. Calls captured before this change keep `timing: null`, which is correct: nothing was measured for them, and that must stay distinguishable from measuring zero.

**`GET /calls/baseline` / `GET /internal-calls/baseline`** give one endpoint's `sampleSize`/p50/p95 so a duration can be judged rather than read. Scoped to the exact url (the same path against two suppliers are different endpoints), COMPLETED calls only (a failure's duration measures how long it took to fail), fetched lazily on panel expand — with the list it would fire one aggregate query per row — and against whichever store the call came from, since inbound roots aren't in `calls.db`. `sampleSize` is part of the answer: under five calls the panel says how few there are rather than presenting a percentile of three as a baseline.
