# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Alfred is a reverse-mode mitmproxy setup that transparently intercepts and logs every HTTPS request/response a Java app sends to any supplier whose configured hostname ends in `-proxy`. It requires zero configuration changes in the Java app itself — no proxy settings, no code changes. Instead, a hosts-file redirect plus a trusted CA cert make the app think it's talking directly to the real supplier.

Three Docker services (see `docker-compose.yml`):
- **alfred** (mitmproxy, `127.0.0.2:443`->8080) — intercepts, dynamically routes `*-proxy` hostnames to their real backend by stripping the suffix, and POSTs each finished call to pennyworth's webhook - it persists nothing itself (see "Real-time updates" below). Bound to `127.0.0.2` rather than all interfaces, on 443 (the HTTPS default) so `-proxy` URLs never need an explicit port, without conflicting with anything already on `127.0.0.1:443` - `start.ps1`/`start.sh` point `-proxy` hosts entries at `127.0.0.2` to match, since all of `127.0.0.0/8` is loopback.
- **pennyworth** (Spring Boot backend, port 5000; multi-module Maven reactor - one module per vertical slice, hexagonal internally, see below) — owns all persistence: recent calls (`backend/data/RECENT_CALLS.log`, a ring buffer capped at `alfred.calls.max-limit` calls - default 200, env `RECENT_CALLS_MAX_LIMIT` - written after each webhook call) served over a small HTTP API (`GET /calls`, `GET /health`), a small comments API (`GET/POST /comments`, `DELETE /comments/{id}`) backed by a flat JSON file (`backend/data/comments.json`), a **session-cycles** API (`GET/POST /session-cycles`, `PATCH`/`POST .../record`/`POST .../pause`/`DELETE .../{id}`, `GET`/`DELETE .../{id}/calls[/{callId}]`) for named recordable/pausable groups of calls (metadata in `backend/data/session-cycles/session-cycles.json`, one captured-calls file per cycle alongside it) - all three inside the same writable volume, see docker-compose.yml - a webhook (`POST /calls/webhook`) the proxy calls on every finished request, and a WebSocket endpoint (`/ws/calls`) that relays those calls (plus which session-cycles just captured each one) to connected dashboards live.
- **manor** (Angular dashboard, built and served via nginx, port 3000) — a tab-nav shell over two views: **Live Calls** (the always-on feed, polls pennyworth every 5s as a resilience fallback and also listens on pennyworth's WebSocket for near-instant updates, with syntax-highlighted flat/tree JSON views, per-block search, sort/pagination, pinning, supplier grouping, cURL/JSON export, and GitHub-style line comments for flagging issues) and **Session Cycles** (create/record/pause/rename/delete named cycles, drill into one to see just its captured calls, remove a stray one, and export - reusing the exact same call-card/export machinery as Live Calls).

## Commands

First-time only, if Docker or Python aren't already installed (safe to re-run - already-installed prerequisites are skipped):

```bash
setup.bat          # Windows, run as Administrator
sudo ./setup.sh    # Linux/macOS
```

Cross-platform entry point (run from an Administrator/root terminal):

```bash
python3 start.py
```

This does all of the following, safe to re-run any time (already-done steps are skipped):
1. Adds missing `*-proxy` hosts entries from `suppliers.txt`
2. Runs `docker compose up -d --build` (generates the CA cert on first run)
3. Re-syncs the CA cert into the OS certificate store
4. Re-syncs the CA cert into every JDK listed in `jdks.txt`, plus the current `JAVA_HOME` environment variable if set

It detects the OS and delegates to `start.ps1` (Windows, via `certutil`) or `start.sh` (Linux/macOS, via `update-ca-certificates`/Keychain, run with `sudo`).

To (re)start containers without redoing the hosts/cert steps:

```bash
docker compose up -d --build
```

Stop everything:

```bash
docker compose down
```

Watch logs live (recent calls live in pennyworth's own file, not the proxy's - it's a ring buffer capped at `RECENT_CALLS_MAX_LIMIT`, default 200):

```bash
Get-Content .\backend\data\RECENT_CALLS.log -Wait -Tail 20 | jq .
```

There is no test suite, linter, or build step for `alfred` beyond the Docker build itself. `pennyworth` and `manor` both have real test suites:

```bash
cd backend
mvn test            # JUnit 5 + Mockito + AssertJ - application services, file adapters, and a @WebMvcTest controller test
mvn package          # full build, produces the Spring Boot jar Docker packages

cd frontend
npm install
npm test           # ng test - Karma/Jasmine, watches by default
npm run build       # ng build - production build, output in dist/manor/browser
```

## Architecture notes

- **Routing happens in two places for a reason** (`proxy/log_and_route.py`): `server_connect` sets the actual TCP/TLS dial target using the client's TLS SNI (captured before the HTTP request is parsed), while `request()` rewrites the logical `flow.request.host`/`Host` header for logging consistency. In reverse mode, mutating `flow.request.host` alone does NOT change where mitmproxy actually connects — both hooks are required.
- **SNI, not `Host` header, is the source of truth** for the original hostname throughout the addon, since in reverse mode `flow.request.host` starts out pinned to the static placeholder (`https://placeholder.invalid`, set in the `mitmdump` command in `docker-compose.yml`).
- **Suppliers and JDKs are config, not code**: `suppliers.txt` lists real domains (no `-proxy` suffix — scripts add it), `jdks.txt` lists `JAVA_HOME` paths needing cert trust. Both support `#` comments and are re-read/re-applied idempotently on every `start.py` run.
- **Per-folder CA identity**: `proxy/certs/` holds a CA generated fresh on first container start, unique to that project folder. Only one Alfred folder's CA can be trusted under the "mitmproxy" friendly name at a time per OS/JDK truststore — running `start.py` from a different Alfred folder re-syncs trust to that folder's CA.
- **Docker cannot touch the host** (hosts file, OS cert store): this is why `start.py`/`start.sh`/`start.ps1` exist as host-side wrappers run outside any container, before/alongside `docker compose`.
- **`setup.bat`/`setup.sh` are a separate, one-time step from `start.py`** - they install the prerequisites (Docker, Python) that `start.py` itself needs to even run, so they can't be part of `start.py`. `setup.bat` (Windows, run as Administrator) and `setup.sh` (Linux/macOS, run with `sudo ./setup.sh`) both check `docker`/`python`(`3`) on PATH first and skip anything already installed. `setup.bat` installs via `winget` (`Docker.DockerDesktop`, `Python.Python.3.12`) since that's the standard trusted package source on modern Windows; `setup.sh` installs via each distro's own package manager (`apt`/`dnf`/`yum`, or Homebrew on macOS) rather than a piped `curl | bash` install script, so nothing here downloads and executes a remote script directly. Neither script touches hosts/certs/Docker containers - that's still entirely `start.py`'s job.
- **JDK cert trust checks `JAVA_HOME` from the environment in addition to `jdks.txt`**, in both `start.ps1` and `start.sh`. `jdks.txt` remains for JDKs that aren't the *current* environment's default (e.g. a server running under a different `JAVA_HOME` than the interactive shell doing the setup); `JAVA_HOME` itself (if set, and not already listed) is appended to the same trust loop automatically, so the common single-JDK case needs zero config-file entries. Deduplicated by exact path match so listing a JDK in both places doesn't double-import it.
- **JVM truststore caching**: a running JVM does not pick up truststore changes live — restart the Java app/server after its JDK's cert import.
- **`frontend/.dockerignore` and `backend/.dockerignore` exist specifically to stop rebuild bloat** - without them, `COPY . .` in each Dockerfile's build stage sends `node_modules` (frontend) or every module's `target/` (backend) into the build context on *every* `docker compose up --build`, which both slows the build and bakes a new, mostly-redundant layer into the local BuildKit cache each time (this is what silently grew the Docker Desktop WSL2 virtual disk past 40GB during heavy same-session rebuilding). `frontend/.dockerignore` excludes `node_modules`/`dist`/`.angular`/`.git`; `backend/.dockerignore` excludes `**/target`/`.git`/`data` (the bind-mounted runtime data dir - never something the image itself should contain). If a rebuild ever again sends a suspiciously large "load build context" size (check `docker compose build <service>` output), the `.dockerignore` for that side is the first thing to check. Since Docker Desktop on Windows never shrinks its WSL2 disk file back down on its own even after `docker builder prune`/`docker image prune` reclaim space internally, an occasional `wsl --shutdown` + `Optimize-VHD -Path <docker_data.vhdx> -Mode Full` (from an admin PowerShell) is the only way to reclaim that space on the actual `C:` drive.
- Payload shape the proxy sends (see README for the full example) always includes both `original_url` (the `-proxy` URL the app called) and `url` (the real forwarded URL), plus method, headers, body, timestamp, duration_ms, and response - identical to the `CallRecord` domain type `pennyworth-calls` persists.
- **The proxy does not persist anything - it only calls the webhook, off a background thread, never inline in a hook.** `response()`/`error()` run synchronously on mitmproxy's asyncio event loop - a blocking HTTP call inside either would stall every concurrent connection being proxied. `_write()` is now just a non-blocking `queue.put_nowait()` (only if `WEBHOOK_URL` is set); a single daemon thread drains that queue and does the actual `urllib.request` POST, swallowing and logging (not raising) any failure. This means `WEBHOOK_URL` is load-bearing, not optional: if it's unset or the webhook is consistently failing, that call is proxied correctly but never recorded anywhere, since pennyworth is now the only thing that writes it down. Stdlib only (`queue`, `threading`, `urllib.request`) deliberately, since `alfred` runs the stock `mitmproxy/mitmproxy` image with no Dockerfile/pip install step.

## pennyworth (backend) architecture notes

`backend` is a Maven multi-module reactor: **one module per vertical slice** (business feature), each internally following hexagonal (ports & adapters) layering. **Every new backend feature or fix must follow this same shape** - this is a binding convention, enforced two different ways (see below), not a one-time cleanup.

```
backend/
├── pom.xml                        packaging=pom, parent=spring-boot-starter-parent, <modules> list
├── pennyworth-platform/            cross-cutting, no feature dependencies
│   └── com.alfred.pennyworth.platform.{config.CorsConfig, web.GlobalExceptionHandler, web.HealthController}
├── pennyworth-calls/                vertical slice
│   └── com.alfred.pennyworth.calls.{domain.model.*, application.port.in/out, application.service, adapter.in.web, adapter.out.filelog}
├── pennyworth-comments/             vertical slice
│   └── com.alfred.pennyworth.comments.{domain.model.*, application.port.in/out, application.service, adapter.in.web(+dto), adapter.out.commentstore}
├── pennyworth-export/               vertical slice - depends on pennyworth-calls (needs CallRecord as input)
│   └── com.alfred.pennyworth.export.{domain.model.ExportMetadata, application.port.in, application.service, adapter.in.web}
├── pennyworth-session-cycles/       vertical slice - depends on pennyworth-calls (implements its NewCallObserverPort)
│   └── com.alfred.pennyworth.sessioncycles.{domain.model.*, application.port.in/out, application.service, adapter.in.web(+dto), adapter.out.filestore, adapter.out.capture}
├── pennyworth-profiles/             vertical slice - a leaf, depends on nothing else
│   └── com.alfred.pennyworth.profiles.{domain.model.*, application.port.in/out, application.service, adapter.in.web(+dto), adapter.out.profilestore}
├── pennyworth-app/                  composition root: depends on all 6 modules above, owns spring-boot-maven-plugin repackage
│   └── com.alfred.pennyworth.PennyworthApplication + application.properties
└── pennyworth-architecture-test/    test-only module, depends on everything, holds the ArchUnit suite
```

**Why modules, not just packages:** a single-module hexagonal layout only enforces its rules by convention - nothing stops a `comments` class from importing a `calls` internal, or a controller from reaching straight into a service. Splitting into one Maven module per slice makes that a *compile error*: a slice's code simply isn't on another slice's classpath unless declared as a dependency. `pennyworth-export → pennyworth-calls` and `pennyworth-session-cycles → pennyworth-calls` are the **two intentional exceptions** (export extracts metadata from a full logged call; session-cycles captures one into whichever cycles are recording) - both one-directional, no cycle back. `pennyworth-profiles` is the opposite case: a **leaf slice** with no dependency in either direction - session-cycles' `assignedTo` only ever stores a profile's id as a plain string, so there's no compile-time coupling at all, just a value that happens to mean the same thing in both slices. Every other cross-slice access is impossible to even attempt, let alone merge.

**Two enforcement mechanisms, two different jobs:**
1. **Maven module boundaries** enforce slice isolation - `calls` cannot depend on `comments`, `export`, or `session-cycles` because there is no `<dependency>` declaring it, full stop.
2. **`pennyworth-architecture-test`'s ArchUnit suite** (`HexagonalArchitectureTest`) enforces everything modules can't: the *direction* of dependencies **within** a slice (domain → application → adapter, never reversed), that domain stays free of `org.springframework` (Jackson is explicitly allowed - see below), that inbound adapters depend on ports and never reach past them into a service class or into an outbound adapter, and that `calls`/`comments` never depend on each other or on `export`/`session-cycles`/`profiles`, that `session-cycles` never depends on `comments`/`export`/`profiles`, and that `profiles` never depends on any other slice. A violation fails `mvn test` - it does not wait for a review comment. (Verified live while building this: temporarily annotating a domain record with `@Component` made exactly one rule fail with a precise message, then reverted.)

**When to add a web DTO vs. reuse the domain type directly:** reuse the domain record across the HTTP boundary when the wire shape and constraints are identical - `CallRecord`, `Comment`, and `ExportMetadata` all qualify today, which is why they're serialized/deserialized directly with no mapping layer in between (mapping code that does nothing but rename fields 1:1 is not "clean," it's noise; this is also why `CallRecord` keeps its `@JsonProperty` annotations and the ArchUnit domain-purity rule explicitly allows Jackson while forbidding Spring). Introduce a distinct `adapter.in.web.dto` type only when the boundary genuinely needs something the domain type doesn't - the one case that exists today is `CommentRequestDto`, which carries Bean Validation annotations (`@NotBlank`, `@PositiveOrZero`) that are a transport concern and don't belong on the domain `NewComment` command.

**Adding a new slice:** create a new `pennyworth-<name>` module (own `pom.xml`, parent = the aggregator), give it the same internal package shape, add it to the aggregator's `<modules>` and to `pennyworth-app`'s dependencies so its beans get component-scanned, and add it to `pennyworth-architecture-test`'s dependencies plus a slice-isolation rule in `HexagonalArchitectureTest` for it. If it needs `@WebMvcTest` coverage, it needs its own tiny test-only `@SpringBootApplication` class (see `pennyworth-comments`' `TestApplication`) - bare `@SpringBootConfiguration` alone does not imply component scanning, only `@SpringBootApplication`/`@ComponentScan` does.

**Persistence is file-based today, and deliberately swappable.** `FileCallLogAdapter` (`RECENT_CALLS.log`), `JsonFileCommentsStoreAdapter` (flat `comments.json`), session-cycles' `JsonFileSessionCycleMetadataStoreAdapter`/`JsonFileCapturedCallsStoreAdapter` (`session-cycles/session-cycles.json` + one `session-cycles/{cycleId}.json` per cycle), and `JsonFileProfileStoreAdapter` (flat `profiles.json`) are plain outbound-port implementations - the application services only ever see their ports (`CallLogPort`, `CommentsStorePort`, `SessionCycleMetadataStorePort`, `CapturedCallsStorePort`, `ProfileStorePort`), never the file I/O behind them. All of it lives in the same writable `/appdata` volume (`./backend/data`) - pennyworth is the sole owner and writer of each file, nothing else on the host or in another container touches them. Each file adapter carries `@ConditionalOnProperty(prefix = "alfred.storage.calls"/"alfred.storage.comments"/"alfred.storage.session-cycles"/"alfred.storage.profiles", name = "type", havingValue = "file", matchIfMissing = true)`, so:
- **Today**: unset (or explicit `file`) means the existing file adapters register, unchanged behavior.
- **Moving to Redis or MySQL later**: write a new adapter class in a new `adapter.out.redis`/`adapter.out.jpa` package implementing the same port, give it `havingValue = "redis"`/`"mysql"`, add the driver dependency to that slice's `pom.xml`, and flip the relevant `alfred.storage.*.type` in `application.properties` (or the env equivalent). Every application service, controller, and the ArchUnit rules all stay exactly as they are - a new adapter is just another class in `adapter.out.*`, which every existing rule already permits.
- Each slice can move independently and at different times (e.g. comments to MySQL while calls and session-cycles stay on files) since each has its own property and its own port(s).

**Profiles are named people/entities that session-cycles' `assignedTo` field references by id - a leaf slice with full CRUD (`GET/POST /profiles`, `GET/PATCH/DELETE /profiles/{id}`).** `Profile(id, name, createdAt, avatar)` is the only domain type - `avatar` is a single emoji character, not a color (the field was originally a hex color and was renamed/repurposed wholesale; see the manor architecture notes below for why). `avatar` is optional on create (`CreateProfileRequestDto`) - `ProfilesService.create` assigns one at random from a small fixed fallback palette (`DEFAULT_AVATAR_PALETTE`, picked via `ThreadLocalRandom` - genuinely random per call, not derived from the id) when none is given; that fallback only matters for direct API use (curl etc.), since manor always sends an already-randomly-chosen avatar on create. `ProfileStorePort.save` is a upsert (`findById` + remove-then-add, matching the file adapter's read-modify-write pattern already established elsewhere) so the same method backs both create and update - `ProfilesService.update` follows the same "null field means leave unchanged" merge convention as `SessionCyclesService.update`/`SessionCycleUpdate`. Adding a field later (e.g. a role) is exactly the three-record-plus-merge-logic change every other domain type in this codebase already takes - nothing about this slice's shape needs to change to grow it.

**Security posture:**
- All inbound web DTOs are validated with Jakarta Bean Validation (`@Valid` in the controller); `GlobalExceptionHandler` (`@RestControllerAdvice`, in `pennyworth-platform`) turns validation failures into a clean `400 {"error": "..."}` body and any unexpected exception into a generic `500` - internal detail (stack traces, file paths) is logged server-side via SLF4J and never sent to the client.
- `GET /calls?limit=` is clamped server-side to `[1, alfred.calls.max-limit]` (default 200, env `RECENT_CALLS_MAX_LIMIT`) regardless of what's requested, so a request can't force an unbounded read - and `RECENT_CALLS.log` itself never grows past that same limit either (see the ring-buffer paragraph below), so the clamp and the file's actual size can't drift apart.
- `DELETE /comments/{id}` and `DELETE /session-cycles/{id}/calls/{callId}` return `404` when the id doesn't exist and `204` when it does - use the boolean a port already returns instead of always answering `200`. `DELETE /session-cycles/{id}` additionally returns `409` while the cycle is recording (must be paused first) - a distinct `DeleteOutcome` enum (`DELETED`/`NOT_FOUND`/`BLOCKED_RECORDING`) drives which status the controller answers with, rather than the controller re-deriving that from separate calls.
- CORS origins come from `alfred.cors.allowed-origins` (env `ALFRED_CORS_ALLOWED_ORIGINS`), not a hardcoded `"*"` - defaults permissive for the current single-team deployment, but tightening for a real deployment is a one-line env change, not a code change.
- Adapters never swallow failures silently: malformed lines and file read/write errors are logged via SLF4J (WARN/ERROR) instead of silently disappearing. Both file adapters check their storage directory is writable at startup (`@PostConstruct`) so a misconfigured volume fails loudly immediately instead of confusingly on the first webhook call or `POST /comments`.
- `POST /calls/webhook` validates `X-Webhook-Secret` against `alfred.webhook.secret` (env `WEBHOOK_SECRET`, shared with the proxy's matching env var) and returns `401` on a mismatch - blank/unset (the default) means open, same permissive-default-tighten-later posture as CORS above, since this port is exposed to the host (`5000:5000`) as well as the docker network.

**The proxy no longer persists anything - pennyworth owns `RECENT_CALLS.log` end to end.** `CallsService.receiveNewCall` (implementing `ReceiveNewCallUseCase`) does `callLogPort.save(call)`, then fans the call out to every `NewCallObserverPort` observer, then `notificationPort.notifyNewCall(call, capturedByCycleIds)` - saved before broadcast, so a dashboard that reacts to the WebSocket push and immediately re-fetches `GET /calls` (or a cycle re-fetches its own calls) always finds the record already there. `FileCallLogAdapter` is both reader and writer of `CallLogPort` (`readAll()` for `GET /calls`, `save()` for the webhook path) - the same file, same class, same never-swallow-failures posture as `JsonFileCommentsStoreAdapter`. `RECENT_CALLS.log` is a **ring buffer, not an unbounded log**: `save()` now does a full read-modify-write (append, then drop from the front if over `alfred.calls.max-limit`) rather than a cheap append, `synchronized` so concurrent webhook calls can't race each other's read-modify-write. `WebSocketCallNotificationAdapter` (`adapter.out.websocket`) is the other half of `receiveNewCall`: it wraps the call in a `CallEvent(call, capturedByCycleIds)` envelope and broadcasts *that* (not the bare `CallRecord` anymore) to every session `CallEventsWebSocketHandler` (registered at `/ws/calls` by `WebSocketConfig`) is tracking. `CallsWebhookController` (`POST /calls/webhook`) is the one inbound adapter that calls `ReceiveNewCallUseCase` - the proxy is the only caller, and it always sends the exact `CallRecord` shape it used to write to `calls.log` itself, reused directly per the DTO-vs-domain-reuse rule above.

**Session-cycles capture new calls without `pennyworth-calls` knowing session-cycles exists.** `NewCallObserverPort` (`List<String> onNewCall(CallRecord call)`, owned by `pennyworth-calls`) is the exact same shape as `CallNotificationPort` - an outbound port the calls slice calls unconditionally (`CallsService` takes `List<NewCallObserverPort> observers`, which Spring injects as an empty list if nothing implements it, so calls compiles and runs fine even without this module on the classpath). `SessionCycleCaptureAdapter` (`pennyworth-session-cycles`' `adapter.out.capture`) implements it: on `onNewCall`, it appends the call to every currently-`RECORDING` cycle's file and returns their ids - any number of cycles can be recording at once, so one call can land in several. Those returned ids are exactly the `capturedByCycleIds` that ride along in the `/ws/calls` broadcast, letting an open session-cycle detail view filter the *same* socket the main dashboard listens to rather than needing one of its own. A captured call is never removed from `RECENT_CALLS.log`/the main feed - capture is additive tagging into a second file, not a redirect. `SessionCyclesService` enforces the one recording-related invariant that isn't just port plumbing: `DELETE /session-cycles/{id}` is blocked (`BLOCKED_RECORDING`) while a cycle is recording, so deleting a cycle can't silently drop calls someone's mid-repro-capturing without a pause first; a successful delete removes both the metadata entry and the cycle's entire captured-calls file (hard delete, no orphaned file left behind). This adds no new ArchUnit exceptions beyond the one `session-cycles → calls` dependency declared in its `pom.xml` (confirmed by running the suite after adding it).

**Testing convention:** application services are unit-tested against fake/mocked ports (`CallsServiceTest`, `CommentsServiceTest`, `ExportMetadataServiceTest`) - no Spring context, no filesystem, because the ports interface is exactly what makes that possible. Adapters get focused tests against a real temp directory (`@TempDir`) rather than mocks, since their whole job is file I/O (`FileCallLogAdapterTest`, `JsonFileCommentsStoreAdapterTest`). Controllers get thin `@WebMvcTest` coverage for HTTP-level concerns only - status codes, validation - with the use cases mocked (`CommentsControllerTest`). `mvn test` at the aggregator (`backend/`) runs the entire reactor including the ArchUnit suite; `docker compose up -d --build pennyworth` uses `-DskipTests` for the image build itself, matching the existing convention of running tests separately from the Docker build.

## manor (frontend) architecture notes

- Standalone Angular components + signals throughout (no NgModules, no NgRx) — `frontend/src/app/core/state/calls-state.service.ts` is the single facade: it polls pennyworth on a 5s timer, merges in live WebSocket pushes, and delegates every filtered/sorted/paginated/grouped/stats view of the data to the shared `createCallListView` factory (`core/state/call-list-view.ts`) rather than computing them inline. That factory is the one place search/sort/supplier-filter/group-by-supplier/collapse-expand/pagination/stats logic lives; `SessionCycleDetailStateService` (below) uses the exact same factory over a session-cycle's captured calls, so a feature added to any of it shows up in both places with no hand-copied second implementation to keep in sync. Components inject state directly, or inject one of the tokens in `call-selection.tokens.ts` when they need to work against either state interchangeably (see the DI-token bullet below).
- **Live updates from pennyworth's WebSocket are additive, never a replacement for polling.** `CallsStateService` opens `rxjs/webSocket` against `${backendUrl}/ws/calls` in its constructor (`retry({ delay: () => timer(3000) })` on disconnect - verified this actually reconnects by restarting the `pennyworth` container mid-session), and pushes each received `CallRecord` into a private `liveCalls` signal. The public `calls` signal is `mergeLiveCalls(liveCalls(), polledCalls())` (`shared/utils/call-utils.ts`) - live-only entries first so they render the instant they arrive, deduped by `callKey` against whatever the poll already returned. A separate `effect()` prunes `liveCalls` down to `unconfirmedLiveCalls(...)` every time a new poll lands, so it can't grow forever; the 5s poll itself is untouched and keeps the dashboard eventually-correct even if the socket never reconnects. Both merge/prune functions are pure and unit-tested directly (`call-utils.spec.ts`) rather than through the service, since exercising a real `WebSocket` in Karma is unreliable.
- **JSON rendering never uses `innerHTML`.** Pretty-printed JSON is tokenized into `{text, cls}` pieces (`shared/utils/json-tokenizer.ts`) and rendered via template interpolation (`shared/components/json-tokens`); the collapsible tree view (`components/json-tree`) is a genuinely recursive component, not a string-built HTML tree. There is nothing here for an XSS payload in a supplier's response body to attach to.
- **Per-block search/filter/view-mode state lives directly on `JsonPanelComponent`, with no external persistence map.** Because the call list's `@for` uses `trackByCallKey` (a stable id derived from timestamp+method+url, not array index), Angular keeps the same component instances alive across every 5s poll instead of destroying and recreating them — so a component's own signals (search query, flat/tree mode, scroll position via the native DOM node) survive automatically. A prior vanilla-JS version of this dashboard had to manually re-apply that state from lookup Maps after every re-render; that entire category of bug is structurally impossible here.
- The one exception is the global "Collapse/Expand all" button: it needs to reach into already-existing panels, so `CallsStateService.collapseAllVersion` is a bump counter each `JsonPanelComponent` watches via an `effect()` — it force-syncs on a version change but otherwise leaves the panel's own toggle alone.
- **Comments are line-scoped and Flat-view-only.** A comment's identity is `(callId, block, lineIndex)` against the *unfiltered* pretty-printed text — `JsonPanelComponent.allLines` computes every line unconditionally and "Lines only" filtering only ever hides indices from `visibleLineIndices`, never renumbers them, so a comment can't silently attach to the wrong line when the filter is toggled. `CommentsStore` caches per-call comment lists so the four panels of a call and its export dialog all read the same fetched data instead of each making their own request.
- **"Open in new tab" reuses `JsonPanelComponent` verbatim - it is not a second implementation.** `JsonViewPageComponent` (routed at `/view`, deliberately outside the tab-nav layout below since it's opened via `window.open`, not in-app navigation) seeds that same component's `[rawValue]/[label]/[callId]/[block]` inputs inside a bigger page layout (a plain CSS override on `.scrollable`, not a component fork). Any feature added to `JsonPanelComponent` therefore shows up in both places automatically - there is deliberately no editing capability anywhere; the JSON is always read-only. `nginx.conf` needs `try_files ... /index.html` because `/view` is opened via `window.open` as a fresh HTTP request, not an in-app navigation, so without the SPA fallback nginx would 404 it. - **Session Cycles: one root-provided list facade, one component-provided detail facade.** `SessionCyclesStateService` (root, `core/state/session-cycles-state.service.ts`) polls `GET /session-cycles` on the same 5s-timer pattern as `CallsStateService` and exposes create/rename/record/pause/delete, each refreshing the list immediately after. `SessionCycleDetailStateService` is deliberately **not** root-provided - it's added to `SessionCycleDetailComponent`'s own `providers`, so navigating from one open cycle to another gets a fresh instance instead of leaking the previous cycle's selection/live state. It polls `GET /session-cycles/{id}/calls`, opens its *own* `webSocket<CallEvent>('/ws/calls')` connection (independent of `CallsStateService`'s - two sockets, not a shared one, kept simple deliberately) and only reacts to a message when `capturedByCycleIds` includes its own route `:id`, and implements both selection interfaces above over `CapturedCall[]` rather than `CallRecord[]`. A cycle's own captured-calls list defaults to **oldest-call-first** (`SessionCycleDetailStateService` passes `{ defaultSortMode: 'oldest-call' }` to `createCallListView`) since a repro usually reads better in the order the calls actually happened - the dashboard keeps its `newest`-first default; `createCallListView`'s `CallListViewOptions` parameter is what makes the two independently configurable from the one shared factory.
- **`'newest'`/`'oldest'` and `'newest-call'`/`'oldest-call'` are deliberately different sort modes, not two names for the same thing.** `'newest'`/`'oldest'` (`sortCalls` in `shared/utils/call-utils.ts`) just reverse whatever order the list already arrived in - capture/received order, which for a session-cycle is *insertion* order into that cycle's file, not necessarily when the underlying call actually happened (a call captured live jumps to the front regardless of its own `timestamp`). `'newest-call'`/`'oldest-call'` instead sort explicitly by `call.timestamp` (parsed via a small `callTime()` helper that treats an unparseable/missing timestamp as epoch 0 rather than throwing), so the order is stable and correct regardless of capture order. Both pairs are selectable from the same `HeaderComponent` dropdown in every context; only the *default* differs (cycles start on `'oldest-call'`, the dashboard starts on `'newest'`).
- **The Session Cycles list itself has its own search/sort/pagination/bulk-selection surface, separate from the `CallListView` machinery (which is `CallRecord`-shaped, not `SessionCycle`-shaped).** `SessionCyclesStateService` adds `searchQuery`/`sortMode`/`selectedIds` signals and `matchingCycles` (name-or-assignedTo substring match, case-insensitive) → `sortedCycles` (`newest` default / `oldest` / `status` - `RECORDING` cycles first, tie-broken newest-first) → `visibleCycles`/`remainingCount` (same page-size "Load more" pattern as the calls list, `PAGE_SIZE = 10`). Bulk actions (`bulkStartRecording`/`bulkPauseRecording`/`bulkReassign`/`bulkDelete`) all fan out to the *existing* single-cycle endpoints via `forkJoin` - one HTTP call per selected id, run concurrently - rather than needing a dedicated bulk endpoint on the backend, the same "no new bulk endpoint needed" shape the copy-to-cycles dialog already established. `bulkDelete` pre-filters out any selected cycle whose `status` is already `RECORDING` (never even sends those to the backend) and returns `{deleted, skippedRecording}` so the UI can report a partial-success summary instead of failing the whole batch over one still-recording cycle.
- **`BulkReassignDialogService.open()` resolves three distinct outcomes, not two.** `undefined` means the user cancelled; `string | null` means they submitted, with `null` specifically meaning "field left blank - clear assignedTo on every selected cycle." Collapsing "cancelled" and "submitted blank" into the same `null` would silently no-op a deliberate bulk-unassign, so the dialog is careful to keep them distinguishable - `SessionCyclesListComponent.bulkReassign()` only bails out on `undefined`, and passes `null` straight through to `bulkReassign()` as a real value.
- **Live-merge for captured calls is keyed by the underlying call's `callKey`, not `CapturedCall.id`.** A live-pushed `CallEvent` only carries a raw `CallRecord`, not the real backend-assigned `CapturedCall.id` (that only exists once persisted and read back via `GET .../calls`) - so `mergeLiveCapturedCalls`/`unconfirmedLiveCapturedCalls` (`shared/utils/call-utils.ts`, mirroring `mergeLiveCalls`/`unconfirmedLiveCalls`) dedupe on `callKey(c.call)` exactly like the dashboard's own live/polled merge, not on the wrapper id. The live-only entry uses that same `callKey` as a placeholder id until the next poll confirms it with the real one. `SessionCyclesService.listCalls` (backend) reverses the captured-calls store's insertion order to newest-first before returning, matching `GET /calls`' convention - the store itself stays oldest-first/append-order, same separation `CallLogPort.readAll()`/`CallsService.getCalls()` already established.
- **`window.prompt`/`window.confirm` are replaced by styled in-app modals, following the exact same one-signal-service-plus-one-mounted-component shape `ExportDialogService`/`ExportDialogComponent` already established.** `ConfirmDialogService.confirm(message)` and `EditCycleDialogService.open(cycle)` both return a `Promise` instead of a synchronous value - callers `await` them (`SessionCyclesListComponent`/`SessionCycleDetailComponent`'s `delete`/`edit` methods are `async` for this reason). `EditCycleDialogComponent` is the only place a cycle's `assignedTo` can be edited - there's no separate control for it elsewhere, since editing name and assignedTo together in one form is simpler than two separate flows for two fields on the same record. `CallCardComponent.remove()` is also `async` for the same reason - it `await`s `ConfirmDialogService.confirm(...)` before calling `removalState.remove(call)`, so removing a call from a cycle asks first exactly like deleting a cycle does. Each page that can render a removable card or trigger a delete (`session-cycles-list`, `session-cycle-detail`) mounts its own `<app-confirm-dialog/>`/`<app-edit-cycle-dialog/>`, same one-instance-per-page pattern as `<app-export-dialog/>` - the dashboard mounts neither, since nothing there is removable and it has no delete action.
- **Each session-cycle row has an "Open in new tab" action** (`window.open('/cycles/' + id, '_blank')`) - no `sessionStorage` bridge needed here unlike the JSON-panel case, since a cycle's detail view is fully re-derivable from its URL alone (`GET /session-cycles/{id}`, `GET .../calls`); nginx's existing catch-all SPA fallback (`try_files ... /index.html`) already serves any deep path including `/cycles/{id}` directly, so no nginx changes were needed. Each tab is a fully independent app instance (own poll, own WebSocket, own component-provided `SessionCycleDetailStateService`), so watching several cycles side-by-side in separate browser tabs has no shared-state pitfalls to design around.
- **A bulk selection can be duplicated into any number of session-cycles, from either the dashboard or a cycle detail page - same `BulkActionsBarComponent`, same "Duplicate to cycles" button, no new component per context.** `CopyToCyclesDialogService.open(calls)` stores the selected `CallRecord[]`; `CopyToCyclesDialogComponent` reads the cycle list straight from the already-root-provided, already-polling `SessionCyclesStateService` (no separate fetch) and renders one checkbox per cycle. Confirming calls `SessionCyclesApiService.copyCallsInto(cycleId, calls)` once per checked cycle (`forkJoin`, not sequential) and shows a combined "Copied N calls into M cycles" message with a skipped count if any. `POST /session-cycles/{id}/calls/copy` (backend, `CopyCallsToCycleUseCase`/`SessionCyclesService.copyInto`) works regardless of `RECORDING`/`PAUSED` status - unlike the live-capture fan-out, this is a deliberate one-off action, not tied to recording state. "Already there" is judged by content (`timestamp+method+originalUrl` - the same identity the frontend's `callKey()` uses, mirrored server-side as a private `contentKey()` helper), checked against both the cycle's existing captured calls *and* the rest of the batch being copied in the same request, so copying a selection that contains the same call twice - or re-running the same copy twice - never creates duplicate entries in the target cycle.
- **Comments sync live across every open tab, not just within one.** `CommentsStore` posts the full updated list for a `callId` over a `BroadcastChannel` on every local add/delete, and any other tab that already has that `callId` cached (dashboard or a "view in new tab" page) applies the update reactively - applying an *incoming* broadcast never re-broadcasts, or tabs would echo the same update back and forth forever. A tab that never loaded that call's comments ignores the broadcast entirely rather than speculatively caching it.
- **Bulk export reuses the single-call export dialog rather than forking it.** `CallsStateService.selectedIds`/`selectedCalls` track a bulk selection (checkbox per `call-card`, keyed by `callKey()`, independent of sort/filter/pagination). `ExportDialogService.open()` now always takes `calls: readonly CallRecord[]` + `commentsByCallId: ReadonlyMap<string, Comment[]>` + a `format: 'markdown' | 'json'`; a single-call export (`CallActionsComponent`) is just the length-1 case of the same call. `ExportDialogComponent.confirmExport()` branches only on `calls.length` and `format` - N=1 markdown still calls the original, untouched `buildExportMarkdown`; N>1 markdown calls `buildBulkExportMarkdown` (numbered summary table with per-call anchors, metadata written once); any JSON export calls `buildBulkExportPayload`. Metadata in the form is always pre-filled from the *first* selected call in current list order, per the user's requirement that the form appear once even for a multi-call export.
- **`BulkActionsBarComponent` is always rendered, not just once something's selected** - with nothing selected it's a slim "No calls selected" + Select all; once `selectedCalls().length > 0` it grows (an animated border/background transition, not a hard show/hide) to add Deselect all and Export .md/.json/cURL. `CallsStateService.selectAll()` selects every call matching the current search/supplier filter regardless of pagination. cURL export deliberately skips the dialog entirely (`buildBulkCurlScript`/`bulkCurlFilename` in `shared/utils/curl-builder.ts`): it's a runnable replay script, not a report, so it only needs a supplier/credentials hint for its header comment, fetched from the first call, rather than the full editable metadata form.
- **No export path truncates or summarizes call data, ever** - a hard correctness requirement, since these exports get handed to another team to diagnose a bug and partial data would read as a false negative. This applies identically to single and bulk .md/.json/cURL exports; test coverage in `markdown-builder.spec.ts`/`bulk-json-builder.spec.ts`/`curl-builder.spec.ts` asserts on large generated bodies specifically to guard this.
- **`ExportDialogComponent`'s "Copy to Clipboard" button copies exactly what "Export" would have downloaded, never a separate rendering.** `ExportDialogComponent.buildContent()` is the single place that turns the current form fields + calls into a markdown string, a JSON payload, or an HTML document (`ExportFormat = 'markdown' | 'json' | 'html'`); `confirmExport()` and `copyToClipboard()` both call it and only differ in what they do with the result (`downloadText`/`downloadJson` vs. `navigator.clipboard.writeText`, JSON-stringified for the clipboard case since `downloadJson` handles that serialization itself). Copying doesn't close the dialog (unlike exporting) so a user can copy, tweak a field, and export afterward. Feedback follows the same signal-plus-`setTimeout` pattern as the existing cURL-copy button in `CallActionsComponent` (button text flips to "Copied!" for 1.2s).
- **HTML export (`shared/utils/html-builder.ts`) produces a single self-contained `.html` file with its own live search/copy/syntax-highlighting, not a static report.** Structurally it mirrors `markdown-builder.ts` exactly (metadata table, flagged-issues summary, Request/Response sections) but each Headers/Body block renders as an empty `<details data-block-id="...">` shell in the HTML body; a `JSON_BLOCKS` config array (one entry per block, generated from the same `Comment[]` data the `.md` export already consumes) drives a single shared `<script>` at the end of the document that builds every block's line-numbered, syntax-highlighted, searchable, copyable UI - so a bulk export with N calls × 4 blocks doesn't duplicate that logic N times. The tokenizer/classifier inside that script is ported line-for-line from `json-tokenizer.ts` (verified against the live app's actual computed colors: key `#c4b5fd`, string `#6ee7d8`, number `#fb923c`, bool `#f472b6`) so highlighting matches pixel-for-pixel. Copying a block appends `// FLAGGED: ...` inline on any commented line (same convention as `codeBlock()`'s inline markers) and joins with real `\n`, and falls back from `navigator.clipboard.writeText` to `document.execCommand('copy')` via a hidden textarea since this file is meant to be opened by double-clicking it from disk, where the Clipboard API is frequently unavailable. Any `</script>` sequence inside embedded call data (e.g. an HTML response body) is escaped to `<\/script>` before embedding so it can't prematurely close the tag - `html-builder.spec.ts` guards this and the never-truncate rule (scoped to the JSON-escaped payload inside the trailing `<script>`, not the whole document, since the shared script's own "Find in block..." placeholder text isn't call data).
- **The whole call-card is a selection target, not just its checkbox.** `CallCardComponent` listens for `mousedown`/`mouseenter`/`window:mouseup` on its host element: mousedown outside an interactive descendant (`SELECTION_EXEMPT_SELECTOR` in `call-card.component.ts` - buttons, links, inputs, the checkbox's own `<label>`, `.uri-value`, `app-call-actions`, `app-json-panel`) toggles that card via `CallsStateService.startDragSelect()`, and dragging from there across other cards' `mouseenter` paints the *same* resulting state onto each one via `dragSelectOver()` - so a drag that starts by selecting always keeps selecting, and one that starts by deselecting always keeps deselecting. URLs and JSON panel content stay normal, copyable text (`cursor: text`/`user-select: text` overrides in styles.scss) since those are exactly what gets copied out of this tool most often; the rest of the card is `user-select: none` so dragging across it doesn't also highlight text.
- **Every JSON block in a .md export is individually collapsible, and its label *is* the toggle.** `codeBlock()`/`headersBlock()` in `markdown-builder.ts` wrap each fenced block in a GitHub-Flavored-Markdown `<details><summary>Headers</summary>`/`<summary>Body</summary>` (collapsed by default, no `open` attribute) via the shared `collapsibleSection()` helper - there's no separate heading sitting above a generic "Show JSON" toggle. This is purely a presentation wrapper around the same never-truncated fenced content used everywhere else (single and bulk .md exports both go through this), so all the existing truncation-guard tests keep passing unchanged.
- **Bulk .md export wraps each call in its own open-by-default `<details>`, with a short identity in the summary line and the full detail repeated in the description below it.** `buildBulkExportMarkdown` renders `<summary><b>Call N</b> <code>METHOD uri</code> STATUS</summary>` using `uriPath()` (`shared/utils/call-utils.ts` - everything after the host, e.g. `api/V2/bundles/GetOfferBundles`, no leading slash or query string; shared by the Summary table's URI column, this heading, and the HTML export's equivalent call heading in `html-builder.ts` - one definition of "the URI" reused everywhere it's shown, not three separate ad-hoc truncations); the full URL, Method, and Status are then repeated as bullets in the description alongside Timestamp/Duration, since a reader who expands a call still wants the complete identity without having to look back at the heading. The Request/Response Headers/Body blocks nest one level deeper inside that (`####`, not `##`), and `flaggedIssuesSection(comments, level)` takes an explicit heading-level parameter (`2` for the single-call export's top-level `##`, `4` once nested inside a bulk call's `<details>`) so "Flagged Issues" never outranks its sibling "Request"/"Response" headings. Metadata is a small table (`metadataTable()`) rather than a bullet list, and `formatMs()` adds thousands separators without forcing a fake ".00" on whole-number durations - both purely presentational, layered on top of the same data every export already had.
- **`.bulk-actions-bar` is only `position: sticky` while something is actually selected (`.active`)** - with nothing selected it's `position: static` and scrolls away with the rest of the page like any other content, since a slim "nothing selected" reminder doesn't need to follow you down the page; once a selection exists it needs to stay reachable while scrolling past the calls/cycles you're about to act on. Two `position: sticky` siblings pinned to the same `top` offset don't stack - the lower `z-index` one disappears behind the higher one once scrolled, rather than sitting visibly below it - so `header` (sticky at `top: 0`, `z-index: 10`) and an *active* `.bulk-actions-bar` can't both use `top: 0`. `HeaderComponent` measures its own rendered height via a `ResizeObserver` (`viewChild.required<ElementRef>('headerEl')` + `ngAfterViewInit`/`ngOnDestroy`) and publishes it as `--header-height` on `document.documentElement` - measured rather than hardcoded because the header's `.controls` row wraps at narrow widths and its title/subtitle text length varies. `.bulk-actions-bar.active` defaults to `top: 0` (correct for the Session Cycles list page, which has no `<app-header>` above it - it's a distinct bespoke `.bulk-actions-bar` div in `session-cycles-list.component.html`, not the reused component); the reused `BulkActionsBarComponent` (used on the dashboard and session-cycle detail pages, both of which do render `<app-header>`) opts into the header-aware offset via a `.below-sticky-header` modifier class on its own root div, which sets `top: var(--header-height)`. Setting `--header-height` globally rather than scoping it would otherwise leak a stale value onto pages without a header.
- **Theming is a single `data-theme` attribute plus one CSS variable block per theme - no component knows a theme switch happened.** `core/models/theme.model.ts` defines the closed `ThemeId` union (`dark` | `light` | `light-glass` | `easy` | `dracula` | `midnight` | `dark-glass` | `slate`) and the `THEMES` list (label + a standalone `swatch` CSS value for the picker button, deliberately independent of the theme's real variables so the swatch renders correctly even before `data-theme` is applied). `ThemeService` (root-provided) holds a `theme` signal, reads/writes `localStorage['alfred-theme']` (there's no login, so "the user's theme" really means "this browser's theme" - a different browser or cleared storage falls back to `DEFAULT_THEME = 'dark'`), and its only side effect is `document.documentElement.setAttribute('data-theme', id)` - both in the constructor (restoring the stored theme on load) and in `setTheme()`. Every themeable surface in `styles.scss` reads one of a fixed set of variables (`--bg`, `--nav-bg`, `--card`, `--card-elevated`, `--card-inner`, `--panel-bg`, `--bg-2`, `--border`/`--border-strong`, `--purple`/`--purple-light`/`--cyan`, `--text`/`--text-dim`/`--text-faint`, `--green`/`--amber`/`--red`, `--tok-key`/`--tok-string`/`--tok-number`/`--tok-bool`/`--tok-null`, `--card-blur`) instead of a literal color, so each of the 7 non-default themes is nothing more than one `[data-theme="..."]` block re-declaring those same names at the bottom of `styles.scss` - `:root` itself holds Dark's values as the default/fallback. Naming deliberately mirrors `shared/utils/html-builder.ts`'s exported-document palette (`--card`, `--card-inner`, `--tok-*`) purely so the two stay easy to keep in sync by eye; they remain fully separate stylesheets with separate concerns (a live themeable app vs. a static exported document) and neither references the other. Frequently-reused tinted overlays (e.g. a translucent purple hover background) use `color-mix(in srgb, var(--purple) 22%, transparent)` rather than a hardcoded `rgba(139, 92, 246, 0.22)`, so they recolor automatically with whatever `--purple` the active theme sets - introducing a dedicated `--purple-tint-*` variable per opacity level would've been needless indirection for something `color-mix` already expresses directly. A few colors are deliberately left as literals rather than themed: the less-common HTTP method badges (PUT/PATCH/DELETE) and status/error pill colors are rare enough and semantically consistent enough that per-theme variation isn't worth the complexity, and the dialog backdrop scrim/box-shadows are plain black by design regardless of theme. `ThemePickerComponent` lives once in `MainLayoutComponent`'s tab-nav bar (not `HeaderComponent`) since the theme it sets is app-wide, not per-page; clicking its button opens a swatch-grid popover (`panelOpen` signal) that closes via a `@HostListener('document:click', ...)` checking `elementRef.nativeElement.contains(event.target)` - simpler than the app's existing backdrop-overlay dialog pattern since this popover doesn't need to block page interaction. Glass themes (`light-glass`, `dark-glass`, and `slate` more subtly) set `--card-blur` above `0px`, applied via `backdrop-filter: blur(var(--card-blur))` on the header/tab-nav. `.tab-nav` additionally needs its own `position: relative; z-index: 11` - `backdrop-filter` establishes a new stacking context, which without that explicit z-index would trap the theme picker's popover (rendered inside the nav) below `header`'s `z-index: 10`, regardless of the popover's own z-index (discovered live: the popover was in the DOM and fully opaque but invisible on screen until this fix).
- **Profiles is a third tab-nav page - a flat list with an inline create form, no search/sort/pagination.** `core/models/profile.model.ts` mirrors the backend's `Profile(id, name, createdAt, avatar)` shape exactly (no web DTO needed, per the reuse rule). `ProfilesStateService` (root-provided) polls `GET /profiles` on the same 5s pattern as `CallsStateService`/`SessionCyclesStateService` but deliberately skips their search/sort/pagination machinery - profile counts are expected to stay small (one team's worth of people) - and adds one thing they don't need: `labelFor(id)`, which resolves a profile id to its name and falls back to the raw id if the profile was since deleted (never silently drops the value). `EditProfileDialogService`/`EditProfileDialogComponent` are the same Promise-based one-instance-at-the-root pattern as `EditCycleDialogService` - name is a text input, avatar is an `EmojiPickerComponent`. `ProfilesListComponent` creates via an inline form (mirroring session-cycles-list's "+ New Cycle" form) rather than a dialog, since creation only ever needs two fields.
- **Profile avatars are single Unicode emoji, not a color swatch or downloaded icon set - `core/models/avatar-emojis.ts` holds a ~350-entry curated pool sourced from Unicode's own published `emoji-test.txt` grouping data (the Smileys & Emotion and Animals & Nature groups in full, plus the neutral single-codepoint entries from People & Body's person/gesture/role/activity/sport subgroups), filtered to single-glyph entries only (no skin-tone/gender modifiers, no flags, no ZWJ sequences) so every avatar renders identically everywhere.** This was a deliberate choice over downloading a third-party SVG avatar pack: Unicode code points aren't copyrightable, every browser already ships the glyphs via its own emoji font (nothing to fetch, license, or keep in sync with an external asset pack), and rendering is just text - no `<img>`, no asset pipeline. `EmojiPickerComponent` (`components/emoji-picker/`) is the same click-to-open/click-outside-close popover shape as `ThemePickerComponent`/`ProfilePickerComponent`, plus a search box (filters `AVATAR_EMOJIS` by name substring - the list is too long to scan by eye) and a "🎲 Random" button that calls the same `randomAvatarEmoji()` helper the create form uses for its default. Unlike those other pickers, its panel is `position: fixed` with `top`/`left` computed in JS from the trigger's `getBoundingClientRect()` (recomputed in `togglePanel()` on every open) rather than plain CSS `position: absolute` - it's opened from inside `.dialog-card`, which has `overflow-y: auto` for dialogs long enough to need scrolling, and this panel (340px tall, taller than the other pickers') was tall enough to get clipped/mispositioned by that ancestor's scroll box when tried as `position: absolute` (confirmed live: the panel rendered detached from its trigger, partly behind the dialog's own footer). Computing fixed coordinates escapes that entirely; the shared `computeFixedPanelPosition()` (see the bullet below) also clamps the left edge to the viewport so the panel never renders partly off-screen for a trigger near the right edge. **A new profile's avatar defaults to a fresh random pick, not a fixed constant** - `ProfilesListComponent.newAvatar` is seeded with `randomAvatarEmoji().char` and re-seeded with a new random pick after every successful create (so the *next* draft starts different too), while `EditProfileDialogComponent` only randomizes as a fallback if an existing profile somehow has no avatar - editing always shows the profile's actual current avatar first, per the effect that seeds `avatar` from `state()`.
- **Session-cycles' `assignedTo` is a profile id, not free text - every place it's entered or shown goes through `ProfilesStateService`.** The "+ New Cycle" form, `EditCycleDialogComponent`, and `BulkReassignDialogComponent` all render `assignedTo` as a `<select>` of `profilesState.profiles()` (value = profile id, plus an "Unassigned" empty-string option) instead of a free-text input. Display is symmetric: `SessionCyclesListComponent.assignedToLabel(cycle)` calls `profilesState.labelFor(cycle.assignedTo)` rather than rendering the raw id, so a row shows "Ada Lovelace" instead of a UUID once profiles exist. `SessionCycle.assignedTo` was already a plain nullable string reserved for exactly this, so wiring it to profiles is mostly a frontend presentation change (see `pennyworth-profiles` being a leaf slice with no compile-time link to `pennyworth-session-cycles`, above) - see the next bullet for the one backend fix this surfaced.
- **`SessionCyclesService.update`'s merge logic treats `name` and `assignedTo` differently, on purpose.** Every other update-style record in this codebase (`ProfileUpdate`, and `SessionCycleUpdate.name` itself) follows "a null field means leave this alone, not clear it." Applying that same rule to `assignedTo` was a real bug, found live: choosing "Unassigned" in `EditCycleDialogComponent` and saving silently kept the cycle's previous assignee, because the PATCH body's `assignedTo: null` was being read as "no change" instead of "clear it." The fix is that `assignedTo` is now always applied exactly as given - `update.assignedTo()` is never null-coalesced against `existing.assignedTo()` - since every actual caller (the edit dialog, bulk reassign) always sends the assignedTo it wants, including `null` to explicitly unassign; there was never a real "leave assignedTo unchanged while updating something else" case to preserve. `name` keeps the null-means-unchanged behavior since `BulkReassignDialogComponent`'s request still needs to omit it.
- **A native `<select>`'s closed box can be themed via CSS, but its open dropdown popup is drawn by the OS/browser and only inconsistently respects page styling - `color-scheme`/`option` colors help but aren't reliable enough, so there are no native `<select>` elements left anywhere in manor.** `:root` sets `color-scheme: dark` (the three light-ish theme blocks - `light`, `light-glass`, `easy` - override it back to `color-scheme: light`) and `select option { background-color: var(--card); color: var(--text); }` (near the top of `styles.scss`) both help native selects look closer to themed in browsers that respect them, but neither is guaranteed across browsers/platforms - verified live that the popup still rendered in the browser's own unstyled palette regardless, for both the assignedTo dropdown and later the limit/sort/supplier-filter dropdowns. `ProfilePickerComponent` (`components/profile-picker/`) was the first replacement - a single-select popover with the exact same click-to-open/click-outside-close shape as `ThemePickerComponent`/`AssignedToFilterComponent` - for the "+ New Cycle" form, `EditCycleDialogComponent`, and `BulkReassignDialogComponent`'s assignedTo field (binds `[value]`/`(valueChange)`, a profile id or `null`, instead of reading `$event.target.value` off a change event). `SelectPickerComponent` (`components/select-picker/`) generalized the same pattern for everything else - any "pick one label from a short fixed list" - taking a plain `{value, label}[]` `options` input instead of being profile-specific; it replaced HeaderComponent's limit/sort/supplier-filter selects (shared by the dashboard and session-cycle detail page) and `SessionCyclesListComponent`'s sort select. Both pickers position their panel `position: fixed`, computed from the trigger's own `getBoundingClientRect()` in JS rather than plain CSS `position: absolute` (see `EmojiPickerComponent`'s note above for why - anything opened inside `.dialog-card`'s `overflow-y: auto` needs this to avoid being clipped/mispositioned).
- **A `position: fixed` popover's coordinates must be computed relative to whatever the browser actually uses as its containing block, which is not always the viewport.** Per the CSS Transforms spec, any ancestor with `filter`, `backdrop-filter`, `transform`, `perspective`, `contain: paint|layout|content|strict`, or a `will-change` referencing one of those becomes the containing block for `position: fixed` descendants instead of the viewport. `header`/`.tab-nav` both set `backdrop-filter: blur(var(--card-blur))` for the glass themes, so `SelectPickerComponent`'s naive `top = triggerRect.bottom` computation rendered a popover exactly `header`'s own distance-from-viewport-top too low - but only in a theme with a non-zero `--card-blur` (e.g. Slate), which is why it wasn't caught while testing in Dark (`--card-blur: 0px`). `shared/utils/popover-position.ts`'s `computeFixedPanelPosition()` is the fix: it walks up from the trigger for the nearest such ancestor and subtracts *that* ancestor's own `getBoundingClientRect()` offset from the target coordinates, so the same call is correct whether the resolved containing block is the viewport, `header`, or (as already worked before this fix, coincidentally - `.dialog-backdrop` is `position: fixed; inset: 0`, so its origin already matches the viewport's) `.dialog-backdrop`. Both `EmojiPickerComponent` and `SelectPickerComponent` call this one shared function rather than each computing their own coordinates - `ProfilePickerComponent`/`AssignedToFilterComponent` don't need it at all since they use plain CSS `position: absolute`, which isn't affected by this. Covered by `popover-position.spec.ts` (no-containing-block case, the exact live Slate numbers that exposed the bug, and the right-edge clamp).
- **The Session Cycles list has a multi-select "Assigned to" filter, not a second free-text search - `AssignedToFilterComponent` mirrors `ThemePickerComponent`'s popover shape with checkboxes instead of swatches.** An empty selection (`SessionCyclesStateService.assignedToFilter`, a `ReadonlySet<string>`) means "all assigned-to values" - the default - rather than "match nothing"; `matchingCycles` ANDs this filter with the existing search-query match so both narrow the list together. `UNASSIGNED_FILTER_KEY` (`'__unassigned__'`) stands in for `assignedTo === null` in the filter set, safe from collision since it's not a valid profile UUID - the same key format the button's own option list and `toggleOption`/`isChecked` use, so there's one definition of "how unassigned is represented in a filter set," not two. `AssignedToFilterComponent` composes `ProfilesStateService` (for the checkbox list of names) and `SessionCyclesStateService` (for the actual filter signal) rather than owning any filter state itself - the component is pure UI over `cyclesState.assignedToFilter`/`setAssignedToFilter`, which is what let `matchingCycles`' existing tests extend cleanly with filter-only and filter+search-combined cases.
